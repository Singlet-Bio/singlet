\section{Methods}
\label{sec:methods}

\subsection{Datasets}
We selected \nm{nDatasets} public datasets distributed as count matrices and in common use in the single-cell
community, spanning droplet (3$'$, 5$'$, nuclei and probe-based), combinatorial-indexing, plate-based (UMI and read
counts), multimodal (RNA with chromatin accessibility peaks or surface-protein tags) and spatial (sequencing- and
imaging-based) protocols, from $10^3$ to above $10^6$ cells (Table~\ref{tab:datasets}). Each is downloaded from its
primary repository at a fixed accession and file, checked against a recorded SHA-256, and converted to a canonical form:
a CSC matrix with features as rows and cells as columns, unsigned 32-bit counts, no explicit zeros, and the feature
identifiers and cell barcodes of the source. Matrices whose stored values are not integers are rejected rather than
rounded. Where a dataset holds several modalities, each count matrix is a separate benchmark unit. The list, with
accessions, licences and conversion notes, is \texttt{datasets.yaml}. Two non-biological count matrices (bulk RNA-seq
gene counts and a bag-of-words corpus) are run as an extension.

\subsection{Formats}
Every format is written from the canonical matrix by its own library with the options a user would choose by default
or that its documentation recommends (Table~\ref{tab:formats}): Matrix Market with gzip; the Cell Ranger HDF5 layout;
AnnData \texttt{.h5ad} uncompressed and with gzip or lzf; AnnData Zarr; loom (only where the dense chunked layout fits
in the run budget); R \texttt{dgCMatrix} saved with \texttt{saveRDS} using gzip or xz; a TileDB-SOMA experiment; a
BPCells matrix directory; COO triplets in Parquet with zstd; and the CSC arrays raw and with zstd level 19. Every file is
read back and compared with the canonical matrix, counts, identifiers and barcodes; a format that fails the comparison
is reported as a failure, not dropped. An R \texttt{dgCMatrix} holds at most $2^{31}-1$ non-zeros, so for larger
matrices the RDS formats cannot store the matrix and BPCells, which stores it, cannot read it into memory; both are
reported as not applicable there, and BPCells is left out of the minibatch panel for those matrices. Size is the total bytes of all files of the format, divided by the number of
non-zeros. \sone{} files are written by the \texttt{singlet} writer with default settings; the ``shared pack'' variant
stores gene identifiers in a separate vocabulary file whose size is not counted, as it is shared by every dataset of the
same annotation.

\subsection{Read speed}
Each configuration runs in a fresh process pinned to $p$ cores (headline $p=\nm{threadsHeadline}$; every format at $p=1$
and $p=\nm{threadsHeadline}$, and \sone{}, AnnData with gzip and the raw CSC arrays also at $p \in \{1,2,4,8\}$), with
three timed repeats; we report the median and keep every time. ``Cold'' reads evict the file from the operating system's
page cache (\texttt{posix\_fadvise(POSIX\_FADV\_DONTNEED)}) before every repeat; they cannot evict the disk controller's
own cache. ``Warm'' reads, at $p=\nm{threadsHeadline}$ only, follow one untimed warm-up read. In Python a read longer
than 60\,s is timed once; in R every repeat is timed. Matrices above $4\times10^8$ non-zeros (\texttt{decode.big\_nnz} in
\texttt{config.yaml}) are timed, cold and warm, at $p=\nm{threadsHeadline}$ from the node's disk only, for the CSC arrays,
the Cell Ranger HDF5, AnnData uncompressed and with gzip, AnnData Zarr, TileDB-SOMA and both \sone{} variants. The timed
interval is the library's own read, from opening the file to the object it returns: a SciPy matrix with gene identifiers
and barcodes, an AnnData object, or the equivalent R object. Converting that object to the canonical matrix and checking
it, which the write stage does for every format to verify the round trip, is not timed. \sone{} is timed in source gene
order, as every other format returns it, and also in its stored order. The rate is non-zeros per second. For \sone{} we
also time the codec alone, from the member in memory to CSC arrays, through the Python binding and in a C++ program that
links the header-only library, for each instruction set (scalar, AVX2, AVX-512) and both gene orders, and record which
kernel actually ran: a request the CPU cannot serve falls back to the next one.

\subsection{Minibatch loading}
Four datasets form the loader panel, from small to the largest tier and from droplet, combinatorial and plate
protocols. A workload is a seeded sequence of minibatches of 512 cells, each made of eight blocks of 64 consecutive cells
at random offsets, which is how block-shuffling loaders read~\cite{dascenzo2025scdataset}. Loaders: AnnData in memory and
in backed mode, AnnData Zarr read lazily, scDataset over backed AnnData, TileDB-SOMA ML, BPCells (R), and the \sone{}
streaming reader (\texttt{singlet.torch.S1Stream}) in stored and source gene order. The Python loaders return each
minibatch as a \texttt{torch.sparse\_csr\_tensor}; BPCells is timed to an R sparse matrix, without conversion to a tensor.
scDataset and TileDB-SOMA ML use their own samplers, configured to the same workload: blocks of 64 cells, one minibatch
per read and no larger shuffle buffer. The \sone{} reader plans the byte ranges of a minibatch's blocks from the chunk
index and sends them together, up to eight at a time over HTTP (\texttt{urllib3}); it is also run sending them one at a
time. It decodes all of a minibatch's runs of cells in one call of the C++ codec, which releases Python's interpreter lock,
decodes the runs in parallel and writes them into one CSR, and, as \texttt{singlet.torch.S1Cells} does by default, sends
the next minibatch's requests while one decodes. TileDB-SOMA ML prefetches with its own reader; the other loaders read
one minibatch after another, as their libraries do. Files are
served from the node's own disk, from the cluster's shared NFS filesystem, and by a local S3-compatible object store
(\texttt{rclone serve s3}) at 0.1, 1 or 10\,Gbit/s with 1\,ms latency, or 1\,Gbit/s with 30\,ms latency. The bandwidth
is a single token bucket over all connections together (our own proxy, \texttt{bwproxy.py}), holding at most 5\,ms of the
tier's rate or 64\,KiB, whichever is larger, so readers that send concurrent requests (the \sone{} reader, TileDB-SOMA,
Zarr through fsspec) share the tier's bandwidth rather than multiply it; a Toxiproxy proxy adds the latency to every
response. At each tier the rate through the proxy without latency is measured with a 1\,GiB transfer over one connection
and over $p$, and recorded: a median of \nm{delivered-s3_0.1g}, \nm{delivered-s3_1g} and \nm{delivered-s3_10g}\,Gbit/s over
$p$ connections at the 0.1, 1 and 10\,Gbit/s tiers. A tier the setup does not reach over $p$ connections
(\nm{cappedTiers}) is flagged. Loaders that cannot read by range download the object first, and that time is
counted; for datasets above the M tier such loaders are not run over the network tiers, and the transfer time of the
object at the tier's bandwidth is reported instead, marked in Table~\ref{tab:minibatch}. We record, from a new process
with a cold cache, the time to open, to read the first minibatch and to build its tensor (three workload seeds; we report
medians), then, for one seed, the sustained rate in cells per second over 200 minibatches after 10 warm-up batches, and
peak resident memory. Library imports are done before timing starts. On a matrix of fewer than $211\times512$ cells the
sustained workload reads some cells twice, and a reader may then serve them from memory; ratios of sustained rates use
only the panel datasets large enough to avoid this. The share of a link a reader fills is its sustained rate times the
file's bytes per cell, divided by the link's bandwidth. From the node's own disk each loader reads its own file, evicted from
the page cache first; the RAID controller's cache cannot be cleared, so the three \sone{} variants, which read the same
file, are cold only for the first of them (\sone{} with requests together), which is the one reported.

\subsection{Payload ladder}
For each matrix we computed the payload size, in bits per non-zero over row indices and values only, of: 32-bit CSC;
LEB128 variable-length integers; row gaps and values as LEB128 in separate streams with zstd at levels 3 and 19; and the
chunk payload of the \sone{} member (rANS tables, row keys and chunks, without header and names).

\subsection{Count models and the floor}
For each matrix we measured the code length that count models assign to it, $\sum_{g,c} -\log_2 p(x_{gc})$ over all
entries including zeros, divided by the number of non-zeros. Cells were split in two halves at random; each model was
fitted on one half and scored on the other, and the halves were swapped (two-fold cross-validation). We charge nothing
for describing a model, so each number is an optimistic bound for a coder that would have to ship it. The models are:
\emph{Poisson}, $x_{gc}\sim\mathrm{Poisson}(s_c\mu_g)$ with $s_c$ the cell's total over the mean total;
\emph{negative binomial}, $x_{gc}\sim\mathrm{NB}(s_c\mu_g,\theta_g)$ with $\theta_g$ by moments, smoothed over mean
expression as in sctransform~\cite{hafemeister2019normalization}; \emph{gene $\times$ depth}, a nonparametric model with,
per gene and per quantile bin of cell depth (32 bins), a presence probability and (in 4 coarser bins) a distribution over
values 1--63 with an Elias-gamma escape above, Krichevsky--Trofimov smoothed~\cite{krichevsky1981performance}; and
\emph{gene $\times$ depth $\times$ cluster}, the same conditioned also on the cell's cluster. Clusters come from
Leiden~\cite{traag2019louvain} on the training half (50 principal components of log-normalised counts; at most 200{,}000 training cells, the rest
assigned to the nearest centroid); test cells are assigned to the nearest training centroid, and each test cell is
charged the entropy of its label. Sparse cluster contexts back off to the gene $\times$ depth estimate with a pseudo-count
of 8. Zero terms of the parametric models are summed per gene and depth bin at the bin's mean depth; on matrices with
at most $5\times10^7$ entries we also summed them exactly, with a largest relative difference of
\nm{nbBinningErrPctMax}\%. The floor of a matrix is the smallest of the four code lengths.

\subsection{Sampling estimate}
For 2{,}000 random test cells we set the cell's profile $\pi_c$ to its normalised counts shrunk toward its cluster's
profile, $\pi_c = (x_c + \alpha\,\bar\pi_{k(c)})/(N_c + \alpha)$, with cluster profiles from the training half and the
weight $\alpha$ chosen by binomial thinning on the sampled cells themselves~\cite{batson2019molecular,neufeld2024inference}
(half of each cell's molecules are held out and their likelihood under the shrunk profile of the other half is
maximised). We then computed the entropy of $\mathrm{Multinomial}(N_c,\pi_c)$, with $N_c$ the cell's total count, as
$-\log_2 N_c! + \sum_g \mathbb{E}[\log_2 x_{gc}!] - N_c \sum_g \pi_{gc}\log_2\pi_{gc}$ under
$x_{gc}\sim\mathrm{Binomial}(N_c,\pi_{gc})$, summing the binomial expectation exactly where $N_c\pi_{gc}<30$ and by a
second-order expansion above. This estimates the information in which molecules were sampled given the profile. Because
$\pi_c$ is a plug-in estimate that uses the cell's own counts, it is not a bound; it is reported for UMI matrices only,
per non-zero and as a fraction of the \sone{} payload per non-zero of the whole matrix.

\subsection{Second-pass compression}
Each \sone{} file was compressed again with zstd \texttt{-{}-ultra -22}, xz \texttt{-9e}, brotli \texttt{-q 11} and
bzip2 \texttt{-9}, and we report output over input size.

\subsection{Ecosystem}
For two datasets we timed, from a cold file, the calls of Fig.~\ref{fig:eco} and the usual reader of the same data
(\texttt{anndata.read\_h5ad}, \texttt{scanpy.read\_10x\_h5}, Seurat \texttt{Read10X\_h5}, which returns a bare matrix,
and \texttt{CreateSeuratObject} over it, which returns the object \texttt{singlet::load(as = "seurat")} returns, and
zellkonverter \texttt{readH5AD}). Python results are compared with the canonical matrix; R results with the matrix
\texttt{Read10X\_h5} returns, itself verified against the canonical matrix by the write stage's round trip. The C++ row
times opening and decoding a member already in memory.

\subsection{Hardware, software and reproducibility}
Every timed job had 8 cores of a shared node of one type (\nm{cpu}, \nm{cores} cores, \nm{memGB}\,GB memory, node-local
\nm{localDisk}), ordinary cluster nodes rather than ones with fast local storage, with at most one of our timed jobs per
node and other users' jobs beside it, and with software versions as in Table~\ref{tab:formats}. Readers used
\nm{threadsHeadline} threads unless a thread count is given. The pipeline is \texttt{python -m s1bench} in \texttt{papers/manuscripts/s1-format/bench} of
the \texttt{singlet} repository: stages \texttt{fetch}, \texttt{canon}, \texttt{write}, \texttt{decode}, \texttt{ladder},
\texttt{floor}, \texttt{second}, \texttt{minibatch}, \texttt{eco} and \texttt{report}, with all settings in
\texttt{config.yaml}, the software environment in \texttt{environment.yml}, and the exact versions that ran (conda
export, the BPCells and Toxiproxy releases, and per-run host records) in \texttt{results/}. The Slurm scripts that ran
it on the cluster are in \texttt{bench/slurm/clipper}. The \texttt{report} stage writes every
plotted value to \texttt{generated/*.tsv} and every number in the text to \texttt{generated/numbers.tex}; the figures
and tables of this paper are drawn by \LaTeX{} from those files, and no result is typed by hand.
