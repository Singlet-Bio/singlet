\section{Discussion}
\label{sec:discussion}

Single-cell count matrices have been stored as generic arrays, handed to compressors that cannot see what the bytes mean,
and the cost is paid every time the data cross a network. \sone{} instead describes the counts with what is known about
them. Its files are several times smaller than the formats in common use and within a few percent of the best count models
we fitted, so in size no lossless format can improve on it by more than single-digit percentages; most of what is left in
UMI data is the random sampling of molecules itself. Among the codes we measured, none was both as small and faster to
decode, although the trend those codes follow suggests that a code of \sone's size could decode about
\nm{trend-s1-x} times faster.

The practical consequences follow from where data are read. Atlases and model-training pipelines increasingly keep data in
cloud object storage and read the same cells many times. There, the bits per cell on the wire, the number of round trips
needed to fetch a minibatch and the per-request and egress fees set both the speed and the cost of every epoch. A format
that is small, fast to decode and readable in part moves the bottleneck from storage back to the model: in our
measurements a training loader started from a remote \sone{} file in under a second and kept a typical network link busy
without downloading or converting anything first. Because each sample file is named by a hash of its contents, a link or a
citation identifies exactly the bytes that were analysed. The same structure, many small counts with heavy-tailed
frequencies, is found outside single-cell biology; on bulk RNA-seq counts and on a text corpus stored as word counts,
\sone{} files were also less than half the size of compressed AnnData (Supplementary Section~\ref{sec:beyond}).

\sone{} has costs, and they set where it helps most. Its decoder spends more time per entry than byte- or bit-aligned
codes, so it runs at the speed of the network only when there are enough cores for the link: on a fast link served by a
few cores, a larger but faster code delivers more. A faster decoder for a bitstream like \sone's is therefore where
the remaining headroom lies, not a smaller file; until then, \sone{} trades decoding speed for size, the right trade
wherever each decoding core serves less than about \nm{frac-cross-gbit}\,Gbit/s of the link. Its writer needs about three times as much memory as AnnData's, which matters for the largest
matrices. The format stores whole-number counts only and does not hold the rich cell and gene annotations of an AnnData
object, so it complements rather than replaces such containers. It has a single implementation, for which the
specification in the Supplement is meant to make a second possible. And our measurements have limits of their own
(Supplementary Section~\ref{sec:slimits}): all timings come from one type of cluster node; the network experiments used an
object store with controlled bandwidth and latency, and the one real cloud store was read from one location; kernels for
AVX-512 and ARM processors were not measured.

Within these bounds, the case for a shared format is strong. Count matrices are the one object every single-cell analysis
and every model trained on single-cell data reads, and \sone{} stores them close to their information content, reads them
in part from anywhere, and returns exactly the original counts to Python, R and C++. We therefore propose \sone{} as a
standard encoding for single-cell count matrices, for archives, atlases and training pipelines alike, and the
\texttt{singlet} package makes it available today.
