\section{Introduction}
\label{sec:intro}

Single-cell studies now routinely profile hundreds of thousands to millions of cells, reference atlases hold tens of
millions~\cite{svensson2018exponential,sikkema2023integrated,czi2025cellxgene}, and a single perturbation screen has
reached a hundred million~\cite{zhang2025tahoe}. These data are no longer analysed once on a laptop. They are served by
atlases to thousands of users and streamed, minibatch by minibatch and epoch after epoch, into machine-learning models
that read every cell many times~\cite{lopez2018deep,theodoris2023transfer,cui2024scgpt}, and more and more often they live
in cloud object storage and cross a network before they are used. Moving the data, rather than computing on them, has
become a bottleneck for large-scale analysis and for building AI-ready datasets.

For a link of a given bandwidth, the number of cells delivered per second is set by how many bits each cell takes. That
number has a floor, the information the counts actually contain, and the formats in use stay far above it. AnnData~\cite{virshup2024anndata},
the 10x Genomics HDF5 file, loom, Zarr and TileDB-SOMA~\cite{tiledbsoma} store a matrix of whole-number counts as generic
arrays and compress them with tools such as gzip or zstd, which see only bytes. Today, therefore, what limits how fast
single-cell data can be delivered is mostly how they are encoded, not the network.

Count matrices are far from arbitrary. Most non-zero counts are exactly one; how deeply a cell was sequenced sets the
expected count of every gene in it; and if genes are numbered from most to least frequently detected, the positions of a
cell's non-zero entries become a short list of small steps. A code that knows these regularities can describe the same
matrix in far fewer bits, as domain-specific formats for sequencing reads did when they replaced gzip with models of their
data~\cite{bonfield2022cram}. Fewer bits help only if they can be decoded as fast as the link delivers them, so two limits
matter together: how few bits a lossless code can spend on the counts, and how fast any code can be decoded.

We set out to measure both limits on real data and to build a format that approaches them. We estimated the information
floor with count models of the kind used in single-cell analysis, and the speed limit with the textbook integer codes a
format could adopt, from raw arrays to entropy coders, each decoding real matrices on one core. We then developed the codec
iteratively with an AI model, Claude (Anthropic), as a coding assistant, measuring each candidate's size and decoding
speed against these limits. The result is \sone, an open format for single-cell count matrices, with the \texttt{singlet}
package that reads and writes it from Python, R and C++. On \nm{nMatrices} public matrices spanning droplet, plate,
combinatorial, multimodal and spatial protocols, \sone{} files were the smallest on every matrix and within a few percent
of the best count models, no code we measured was both as small and faster to decode, and training loaders reading \sone{}
from cloud storage delivered cells tens of times faster than chunked alternatives. We also report what \sone{} costs: its
decoder is slower per core than byte-oriented codes, which matters on fast links with few cores, and its writer needs more
memory than most.
