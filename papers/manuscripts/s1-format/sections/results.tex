\section{Results}
\label{sec:results}

\subsection{\sone{} files are the smallest on every matrix}

\sone{} produced the smallest file on every one of the \nm{nMatrices} matrices (Fig.~\ref{fig:wow}a,
Table~\ref{tab:main}). Against uncompressed sparse arrays, \sone{} compressed a median of \nm{cr-s1} times. The typical
gzip-compressed AnnData file, the most common way single-cell data are shared, was \nm{ratio-h5ad_gzip} times larger than
the \sone{} file, and even the smallest alternative on each matrix was \nm{ratioBestOther} times larger. The gain does not
come from a stronger general-purpose compressor: zstd at its strongest level on the raw arrays, and a cloud-ready Zarr
layout with the same block size as \sone, both left files about twice as large. It comes from describing the counts.
Measured against the code length of the best count model we fitted, three quarters of a gzip-compressed AnnData file is
redundant, and at least \nm{redund-other-min}\% of every other format; for \sone{} the median is \nm{redund-s1}\%
(Table~\ref{tab:main}).

\subsection{Smaller files that are also faster to read}

A smaller file usually costs more time to decompress. We timed every format from a cold file into an in-memory sparse
matrix on four cores, fewer than a current laptop typically has and a small share of a cluster node (the CPU nodes we
used have 40 to 64 cores). On four cores \sone{} was the fastest format on \nm{dec-s1-fastest-count} of
\nm{dec-paired-n} matrices and the only one that was both small and fast (Fig.~\ref{fig:wow}b).

That advantage comes from decoding in parallel. On one core, \sone{} read a median of \nm{dec-s1-t1} million non-zeros per
second, third behind uncompressed CSC arrays and AnnData Zarr, and it was the fastest format on none of the
\nm{dec-paired1-n} matrices measured on one core (Table~\ref{tab:main}). Its decoder spends more time per entry than
byte-oriented codes (Section~\ref{sec:floor}), but it splits each matrix into blocks that decode on separate cores. Most
formats do not decode in parallel at all; among the few that do, \sone{} gained the most from each added core
(Fig.~\ref{fig:wow}d).

\subsection{\sone{} reads at the speed of the network up to 1\,Gbit/s}
\label{sec:network}

When data come over a network, the time to deliver them is the time to transfer the stored bytes plus the time to decode
them. For a format storing $b$ bits per non-zero entry and decoding $D$ entries per second, a link of bandwidth $B$
delivers
\begin{equation}
R_{\mathrm{eff}} \;=\; \left(\frac{b}{B} + \frac{1}{D}\right)^{-1}\ \text{non-zero entries per second}.
\label{eq:reff}
\end{equation}
The model is conservative, since a reader that overlaps transfer and decoding does better. A smaller file helps only if
its decoder keeps up; a reader runs \emph{at the speed of the network} when the link, not the decoder, is the limit.

\input{figures/fig_net}

On four cores \sone{} decodes about as many entries per second (\nm{net-s1-mnnzs} million) as a 1\,Gbit/s link carries in
\sone{} form (\nm{net-s1-at-1g} million), so up to about 1\,Gbit/s the link is the limit. Because each entry takes so few
bits, the same link then carries about twelve times as many entries as \sone{} as it does as uncompressed arrays, and more
than any other format over every common link speed (Fig.~\ref{fig:net}a). Faster links need more cores, and the decoder
scales with them: read from a cold file on a whole \nm{core-max}-core node, \sone{} kept up with a median of
\nm{core-8-gbit}\,Gbit/s on 8 cores, \nm{core-16-gbit}\,Gbit/s on 16, \nm{core-32-gbit}\,Gbit/s on 32 and
\nm{core-44-gbit}\,Gbit/s on \nm{core-max} (medians over \nm{core-n} matrices).

\input{figures/fig3_floor}

Every loader in these experiments delivers decoded data: the time counted runs until the cells have arrived and been
decompressed into PyTorch sparse tensors, so \sone's decoding is part of every rate, not only its smaller transfer.
Reading 512-cell minibatches from an object store whose bandwidth we controlled, the \sone{} loader filled most of a
1\,Gbit/s link and delivered thirty to a hundred times more cells per second than AnnData's Zarr loader or TileDB-SOMA's
loader for machine learning (Fig.~\ref{fig:net}b). Its first minibatch arrived several times sooner than from any other
loader that reads a file in parts, and each later minibatch took a few milliseconds (Fig.~\ref{fig:wow}c).

Latency matters as much as bandwidth: every request waits a full round trip, and cloud storage adds tens of milliseconds
to each. Because the \sone{} index locates every block before any is read, the reader sends all of a minibatch's range
requests at once and requests the next minibatches while one decodes. With the \texttt{singlet} defaults, \sone{} kept
\nm{ns-s1_stream-cps-30} cells per second at 30\,ms per round trip, against \nm{ns-s1_stream-cps-0} with no added delay
(Fig.~\ref{fig:net}c).

Finally, we read the files from a real cloud object store, Cloudflare R2, over the public internet
(Fig.~\ref{fig:net}d). The first minibatch of a 580,000-cell lung atlas arrived in under a second, while downloading the
AnnData file first took well over a minute, and \sone{} then streamed cells tens of times faster than either Zarr layout.
Because it moves fewer bytes in fewer requests, an epoch of random minibatches would cost about twenty times less in
transfer and request fees than with AnnData Zarr, at the prices of a provider that charges for both. \sone{} needs no
extra DataLoader worker processes to reach these rates, since its decoder already uses every core.

\subsection{\sone{} is close to the limits of size and speed}
\label{sec:floor}

How much smaller could a file be? Following the payload of a matrix as ideas are added (Fig.~\ref{fig:floor}a), storing
the steps between entries and compressing them with the strongest general-purpose compressor shrinks the file a lot, but
modelling the counts, as \sone{} does, removes nearly a third of what is left. The best count model we fitted, even though
it was charged nothing for its own parameters, was only a few percent shorter than \sone. For data counted with molecular
barcodes, most of the remaining bits describe which molecules happened to be captured: given a cell's expression rates,
this is a random sample that no lossless format can avoid storing. Nor is anything left for a byte-level compressor:
zstd-19 does not shrink an \sone{} bitstream at all, and a code that treats each step and value on its own cannot go below
\nm{ent-h0-vs-floor} times the floor. Relative to the best count models we fitted, a lossless format could improve on
\sone{} in size by single-digit percentages at most; a richer model, of dependence between genes or between neighbouring
cells, could lower that reference.

How fast could a file be decoded? Timed on one core, the integer codes trade size for speed along a clear frontier
(Fig.~\ref{fig:floor}b). Byte- and bit-aligned codes decode at close to the rate at which a core can merely write the
output, but store three to twelve times more bits than \sone; entropy coders reach small sizes at a fraction of that
speed. \sone{} is the smallest end of this frontier, and no code we measured was both as small and faster. The ideal code,
as small as the best count model and as fast as writing the output, lies far from every measured code.

Is \sone{} slow for its size, or is that the price of being small? The time the other codes spend per entry, beyond
writing the output, grows as a power of how few bits they store. Extrapolated to \sone's size, this trend predicts the rate
a code that small could be expected to reach, and \sone{} decodes at \nm{trend-s1-pct}\% of it (95\% interval
\nm{trend-s1-lo}--\nm{trend-s1-hi}\%): within the uncertainty, it lies on the trend. Reading genes in their source order
instead of the stored order would put it at \nm{trend-source-pct}\%.

What matters in practice is the delivered rate (Eq.~\ref{eq:reff}), and relative to the ideal code it depends on how much
bandwidth each decoding core must keep up with (Fig.~\ref{fig:floor}c). When cores are plentiful relative to the link, as
when a 32-core machine reads from a 1\,Gbit/s connection, \sone{} delivers \nm{frac-s1-32c}\% of what the ideal code would
and more than any other code, because size is what limits. When few cores serve a fast link, the decoder becomes the
limit: above about \nm{frac-cross-gbit}\,Gbit/s per core, zstd's larger but faster stream delivers more. Decoding speed,
not size, is where the remaining headroom lies.

\subsection{Writing cost}

Writing is the price of a small file (Fig.~\ref{fig:floor}d). \sone{} wrote a 580,000-cell atlas faster than
gzip-compressed AnnData, the 10x HDF5 file or TileDB-SOMA, but slower than formats that store raw or lightly compressed
arrays, such as Zarr, BPCells and Parquet, and its writer needed about three times as much memory beyond the input as
AnnData's.

\subsection{\sone{} in the single-cell ecosystem}

A format is useful only if the tools people already use can read it. The open-source \texttt{singlet} package, for
Python and R, integrates \sone{} with each of them (Fig.~\ref{fig:eco}). One call stores a matrix from AnnData, SciPy,
SingleCellExperiment or Seurat, after checking that the file decodes to exactly the input; one call loads it back as any of
these, with the original counts, gene identifiers and barcodes, and loading was faster than reading the equivalent
AnnData or 10x file in both Python and R (Supplementary Table~\ref{S-tab:eco}). Every reader takes a local path or a URL
and fetches only the blocks it needs, so the same code reads a file on a laptop, on a cluster's shared filesystem or in a
cloud bucket.

For machine learning, \texttt{singlet.torch} provides PyTorch datasets that stream decoded minibatches without converting
or downloading anything first: \texttt{S1Cells} serves block-shuffled minibatches from one \sone{} file, and
\texttt{AtlasCells} streams the cells that match a metadata filter from the many \sone{} samples of an atlas, drawing each
minibatch from several samples, mapping every sample onto one gene axis, holding out whole studies for validation and
dividing samples between DataLoader workers and distributed ranks. In C++, a header-only library decodes any range of cells
into CSC arrays. Because a dataset is a manifest of content-addressed files, anyone can check that the bytes they
received are the ones the manifest names.
