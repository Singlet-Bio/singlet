\section{Results}
\label{sec:results}

\subsection{Overview}

We compared \sone{} with the formats single-cell practitioners use: Matrix Market with gzip, the 10x Genomics HDF5
layout, AnnData as \texttt{.h5ad} (uncompressed, gzip and lzf) and Zarr, loom, R \texttt{dgCMatrix} serialized as
\texttt{.rds}, TileDB-SOMA, BPCells, and COO triplets in Parquet (Table~\ref{tab:formats}). To separate what the \sone{}
transform contributes from what a stronger general-purpose codec would give, we also stored the raw CSC arrays
uncompressed and with zstd at level 19. The panel has \nm{nMatrices} count matrices from \nm{nDatasets} public datasets
in \nm{nProtocolClasses} protocol classes, from \nm{fracOnesMinPct}--\nm{fracOnesMaxPct}\% of non-zeros equal to one,
\nm{nnzTotalBillions} billion non-zeros in total (Table~\ref{tab:datasets}). Timings use \nm{threadsHeadline} cores of
a \nm{cpu} node (Section~\ref{sec:methods}).

The question every benchmark answers is the one a user faces: how long until a matrix, or a minibatch of it, is ready
in memory. For a remote file this is request latency plus transfer plus decode, and compression helps only if it
removes more transfer time than it adds decode time. We make this explicit with the \emph{effective delivery rate}
\begin{equation}
R_{\mathrm{eff}}(B) \;=\; \left(\frac{b}{B} + \frac{1}{D_p}\right)^{-1}\ \text{non-zeros per second},
\label{eq:reff}
\end{equation}
where $b$ is the stored size in bits per non-zero, $B$ the link bandwidth in bits per second and $D_p$ the decode rate
on $p$ cores. A format beats a reference ($b_0$, $D_{p,0}$) on a link of bandwidth $B$ exactly when
$(b_0-b)/B > 1/D_p - 1/D_{p,0}$: the transfer time saved must exceed the decode time added.

\subsection{\sone{} is the smallest format and is never the bottleneck}

Across the panel, \sone{} files take a median of \nm{s1BpnMedian} bits per non-zero (range
\nm{s1BpnMin}--\nm{s1BpnMax}) with gene identifiers and barcodes included, and are the smallest file on
\nm{s1SmallestCount} of \nm{nMatrices} matrices (Fig.~\ref{fig:wow}a, Table~\ref{tab:size}). The median matrix is
\nm{ratio-h5ad_gzip}$\times$ smaller than gzip-compressed AnnData, \nm{ratio-tenx_h5}$\times$ smaller than 10x HDF5,
\nm{ratio-soma}$\times$ smaller than TileDB-SOMA and \nm{ratio-bpcells}$\times$ smaller than BPCells; the strongest
alternative, \nm{bestOtherFormat}, is \nm{ratioBestOther}$\times$ larger. Applying zstd at level 19 to the raw arrays
gives \nm{size-csc_zstd19} bits per non-zero, so most of the gain comes from the transform and the model, not from the
entropy coder alone (Section~\ref{sec:floor}). With gene identifiers moved into a vocabulary pack shared by every
dataset of the same annotation, the median falls to \nm{size-s1_pack} bits per non-zero.
% CHECK: s1SmallestCount == nMatrices; if not, name the exceptions (likely the ADT or imaging matrices).

Smaller files are usually slower to read. \sone{} is not. The C++ decoder reads \nm{codec_cpp-native-avx2-t1}
million non-zeros per second on one core and \nm{codec_cpp-native-avx2-t4} million on \nm{threadsHeadline} with AVX2,
against \nm{codec_cpp-native-scalar-t1} million on one core with the portable scalar decoder; all kernels give identical
output (Table~\ref{tab:decode}). On this CPU the AVX-512 kernel is no faster than AVX2
(\nm{codec_cpp-native-avx512-t4} million on \nm{threadsHeadline} cores): decoding is bound by the table lookups, not
by the width of the arithmetic. Through the Python binding, from a cold file on the node's disk to a SciPy matrix,
\sone{} reads \nm{dec-s1-cold-t4} million non-zeros per second, \nm{dec-speedup-best-other}$\times$ the next fastest
format (\nm{dec-best-other-name}), against \nm{dec-h5ad_gzip-cold-t4} for gzip AnnData and \nm{dec-csc_i32-cold-t4}
for the uncompressed arrays, which must move twelve times as many bytes. Fig.~\ref{fig:wow}c places every format on the
size--speed plane with iso-lines of Eq.~\eqref{eq:reff} at 1\,Gbit/s. Measured per matrix, \sone{} delivers non-zeros
faster than uncompressed CSC on \nm{wire-wins-0p1} of \nm{wire-n-0p1} matrices at 0.1\,Gbit/s,
\nm{wire-wins-1} of \nm{wire-n-1} at 1\,Gbit/s and \nm{wire-wins-10} of \nm{wire-n-10} at 10\,Gbit/s (median
gains \nm{wire-gain-0p1}$\times$, \nm{wire-gain-1}$\times$ and \nm{wire-gain-10}$\times$), so the compression pays
for itself on every link we consider.

For machine learning the quantity that matters is the time until a sparse minibatch is ready for the model. From a cold
start, reading \nm{fig1b-dataset} from an object store at \nm{fig1b-tier}, the first 512-cell minibatch is a
\texttt{torch.sparse\_csr\_tensor} after \nm{ttfm-s1}\,s with \sone, against \nm{ttfm-best-other}\,s for the fastest
alternative (\nm{ttfm-best-other-name}; Fig.~\ref{fig:wow}b, Table~\ref{tab:minibatch}). The \sone{} reader needs one
request for a few kilobytes that plan every later read and one request per run of chunks, and it moves only the chunks
that hold the requested cells. Sustained throughput into the model is \nm{thr-s1_stream-s3_1g} cells per second at
1\,Gbit/s, \nm{thr-s1_stream-nfs} from the shared filesystem and \nm{thr-s1_stream-local} from the node's own disk
(Fig.~\ref{fig:wow}d).

Latency, more than bandwidth, sets the cost of reading from an object store: every request waits a round trip, and
cloud object stores take tens of milliseconds to return a first byte. Because the index locates every chunk before any is
read, the \sone{} reader sends all of a minibatch's range requests together, eight at a time over HTTP. On a 1\,Gbit/s
link with 30\,ms latency, the first minibatch arrives in a median of \nm{ttfm-wan-s1_stream}\,s over the panel, against
\nm{ttfm-wan-s1_stream_seq}\,s for the same reader sending its requests one at a time and \nm{ttfm-wan-anndata_zarr_lazy}\,s
for AnnData Zarr, whose reader also sends concurrent requests; sustained throughput on that link is
\nm{concurrency-gain-sustained}$\times$ higher with concurrent requests than without (Fig.~\ref{fig:wow}d). The tiers
limit the total bandwidth of all connections, so concurrent readers share the link rather than multiply it
(Section~\ref{sec:methods}).

\subsection{How \sone{} stores a count matrix}

Fig.~\ref{fig:how} shows the format from a dataset down to the bit stream. A dataset is a small manifest that lists
immutable sample objects named by the SHA-256 of their content (Fig.~\ref{fig:how}a). What a sample shares with other
samples, the gene vocabulary of an annotation and the barcode whitelist of a chemistry, can live in a shared pack that
a reader downloads once and caches. Anything that can be recomputed from the stored data is replaced by a recipe that
the writer runs and verifies byte for byte before it drops the original (Fig.~\ref{fig:how}b).

The count matrix is a \texttt{pz2} member whose first few kilobytes (header, chunk index, entropy tables and row keys)
are enough to plan a read of any set of columns (Fig.~\ref{fig:how}c). Chunks of at most 49{,}152 non-zeros decode
independently, so a reader issues one request for the prefix and one per contiguous run of chunks it needs.

The codec turns each column into a short sequence of small symbols and codes them with static rANS
(Fig.~\ref{fig:how}d). Rows are stored in order of how many cells express them, in classes of four per doubling, so
frequent genes get small row numbers and the gaps between a cell's non-zeros are small; the order is derived from
per-row counts that the file stores anyway, so it costs no permutation. Each non-zero becomes one symbol carrying the
gap class and a flag for counts above one, plus a residual for those counts. The probability table for each symbol is
selected by two contexts every reader knows at that point: how many non-zeros the cell has, and how far down the gene
list the cell has progressed. The tables are counted once per matrix and stored, so decoding is a table lookup, a
multiply and an add per symbol, with no model to update. Thirty-two interleaved rANS states~\cite{giesen2014interleaved}
share one 16-bit word stream, which lets AVX2 and AVX-512 decode eight to sixteen symbols per instruction with output
identical to the scalar decoder. After decoding, every state must return to its initial value, which doubles as an
integrity check of every chunk.

\subsection{\sone{} is close to the best code any count model gives}
\label{sec:floor}

We next asked how much smaller a lossless file could be. Fig.~\ref{fig:floor}a follows the payload (row indices and
values only) as each idea is added, median over the panel. CSC as 32-bit integers costs \nm{ladder-L0_csc_i32} bits
per non-zero; variable-length integers bring this to \nm{ladder-L1_leb128}; row gaps in separate streams with zstd
reach \nm{ladder-L2_gaps_leb_zstd3} at level 3 and \nm{ladder-L3_gaps_leb_zstd19} at level 19. General-purpose coders
stop there because they cannot see which gene a gap belongs to or how deep the cell is. The \sone{} payload is
\nm{ladder-L4_s1_payload} bits per non-zero.

To bound what is left, we fitted count models on half of each matrix's cells and measured their code length on the other
half, with zeros included and no charge for describing the model (Section~\ref{sec:methods}): Poisson and negative
binomial models with a depth factor per cell and parameters per gene~\cite{hafemeister2019normalization,townes2019feature},
a nonparametric model of each gene's presence and value given the cell's depth, and the same model additionally conditioned
on the cell's cluster. The best of these reaches \nm{ladder-floor} bits per non-zero; \sone{} is a median of
\nm{s1AboveFloorPct}\% above it (range \nm{s1AboveFloorPctLo} to \nm{s1AboveFloorPctHi}\%) while decoding with static
tables (Fig.~\ref{fig:floor}b, Table~\ref{tab:floor}). Knowing a cell's cluster, which is the information other cells
hold about it, is worth \nm{sharedBpnMedian} bits per non-zero (range \nm{sharedBpnLo}--\nm{sharedBpnHi}) before the
cost of the model, and a second compression pass over \sone{} output returns \nm{secondMin}--\nm{secondMax} of its size
with every general-purpose coder (Fig.~\ref{fig:floor}d).
% CHECK: sign of gain-nb; the negative binomial should cost more than the nonparametric model on UMI data and may win
% on read counts. State which model is best per protocol class from tab_floor.tsv.

The reason is the data. Given a cell's expression profile, its molecules are a multinomial sample, and which molecules
were captured is information, not redundancy~\cite{grun2014validation,svensson2020droplet}. We computed the entropy of
that sample for each cell under a profile shrunk toward the cell's cluster (Section~\ref{sec:methods}): it accounts
for a median of \nm{samplingPctMedian}\% of the \sone{} code length (range
\nm{samplingPctLo}--\nm{samplingPctHi}\%, Fig.~\ref{fig:floor}c). The rest is what the counts reveal about the cell's own
profile, which a decoder cannot know in advance, and the small margin between \sone{} and the best model.

\subsection{\sone{} in the single-cell ecosystem}

\sone{} is read by the \texttt{singlet} package, which has Python, R and header-only C++ interfaces over the same codec
(Fig.~\ref{fig:eco}). \texttt{singlet.write\_s1} and \texttt{singlet::write\_s1} store a matrix from AnnData, SciPy,
SingleCellExperiment or Seurat, and the result decodes to exactly the input. In Python, \texttt{singlet.load(path)}
returns an AnnData object with counts in \texttt{X}, and \texttt{singlet.torch.S1Cells} is a PyTorch dataset of
block-shuffled sparse minibatches from a local file or a URL, reading one minibatch ahead on a background thread. In R,
\texttt{singlet::load(path, as = "sce")} and \texttt{as = "seurat"} return SingleCellExperiment and Seurat objects.
Each call returns exactly the counts, gene identifiers and barcodes of the source. On pbmc10k\_v3, \texttt{singlet.load}
takes \nm{eco-py-singlet}\,s against \nm{eco-py-read-h5ad}\,s for \texttt{anndata.read\_h5ad}, and in R
\texttt{singlet::load(as = "sce")} takes \nm{eco-r-singlet-sce}\,s against \nm{eco-r-read10x}\,s for
\texttt{Seurat::Read10X\_h5} and \nm{eco-r-readh5ad}\,s for \texttt{zellkonverter::readH5AD} (Table~\ref{tab:eco}). The C++ codec builds without architecture flags and selects the
scalar, AVX2 or AVX-512 kernel at run time.
