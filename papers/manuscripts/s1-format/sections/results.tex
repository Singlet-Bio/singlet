\section{Results}
\label{sec:results}

\subsection{\sone{} files are the smallest on every matrix}

We compared \sone{} with the formats single-cell researchers use, from Matrix Market text files and the 10x Genomics
HDF5 file to AnnData, loom, R objects, TileDB-SOMA and BPCells, on \nm{nMatrices} public count matrices from
\nm{nDatasets} datasets: droplet, plate-based and combinatorial single-cell data, multimodal data and spatial data from
both sequencing and imaging, from a thousand to more than a million cells each (Supplementary
Tables~\ref{tab:formats} and~\ref{tab:datasets}). Every file was read back and checked against the original counts,
gene identifiers and cell barcodes.

\sone{} produced the smallest file on every one of the matrices (Fig.~\ref{fig:wow}a). The typical gzip-compressed
AnnData file, the most common way single-cell data are shared, was \nm{ratio-h5ad_gzip} times larger, and even the
smallest alternative on each matrix was \nm{ratioBestOther} times larger. The gain does not come from a stronger
general-purpose compressor: the best such compressor we tried on the raw arrays, and a cloud-ready Zarr layout with the
same chunk size as \sone, both left files about twice as large (Fig.~\ref{fig:wow}a, grey). It comes from describing the
counts themselves, as the next sections show.

\subsection{Smaller files that are also faster to read}

A smaller file usually costs more time to decompress. \sone{} does not pay that price: read from a cold file into a
sparse matrix, it was the fastest format on most matrices and the only one that was both small and fast
(Fig.~\ref{fig:wow}b). Its decoder spreads the work over the available cores, while reading uncompressed arrays is limited
by the disk and gzip decompression runs on a single core (Fig.~\ref{fig:wow}d). For machine learning, what counts is the
time until a model receives its first minibatch of cells; from cloud-style storage \sone{} delivered it several times
sooner than any other loader that reads a file in parts (Fig.~\ref{fig:wow}c).

\subsection{How \sone{} stores a count matrix}
\label{sec:how}

Fig.~\ref{fig:how} shows the format from a whole dataset down to individual bits (the complete specification is in
Supplementary Section~\ref{sec:spec}). A dataset is a small manifest that lists one file per sample, each named by a
fingerprint (cryptographic hash) of its contents, so a link always refers to exactly the same bytes and anyone can check
them (Fig.~\ref{fig:how}a). Information shared by many samples, such as the list of gene names of a genome annotation, is
stored once and downloaded once (Fig.~\ref{fig:how}b).

Each count matrix starts with a small index that tells a reader where every block of cells lives in the file, followed by
blocks of consecutive cells that can each be decoded on their own (Fig.~\ref{fig:how}c). To read a few hundred cells, a
reader fetches the index once and then only the blocks it needs, with one web request per run of blocks, from a local disk,
a web server or a cloud bucket alike.

Inside a block, genes are numbered from most to least frequently detected, so each cell's non-zero entries become a
sequence of small steps and small counts, most of them ones. Each entry is turned into one short symbol, and the
probability of each symbol is looked up in a table chosen by two things the reader already knows: how many entries the
cell has and how far along the gene list it is (Fig.~\ref{fig:how}d). An entropy coder (rANS~\cite{duda2013asymmetric})
then spends close to the minimum number of bits on each symbol. Because the tables are fixed for the whole matrix, decoding
is a few table look-ups per entry, and 32 coders run side by side so that modern processors decode eight to sixteen
symbols at once. Writing a file ends with a full decode that must reproduce the input exactly.

\subsection{\sone{} reads at the speed of the network}
\label{sec:network}

When data come over a network, the time to deliver them is the time to transfer the stored bytes plus the time to decode
them. For a format storing $b$ bits per non-zero entry and decoding $D$ entries per second, a link of bandwidth $B$
delivers
\begin{equation}
R_{\mathrm{eff}} \;=\; \left(\frac{b}{B} + \frac{1}{D}\right)^{-1}\ \text{non-zero entries per second}.
\label{eq:reff}
\end{equation}
A smaller file helps only if its decoder keeps up; we say a reader runs \emph{at the speed of the network} when the link,
not the decoder, is the limit. On four cores \sone{} keeps up with links of about 1\,Gbit/s, and with faster links on more
cores. Because each entry takes so few bits, the same link then carries about twelve times as many entries as \sone{} as
it does as uncompressed arrays, and more than any other format over every common link speed (Fig.~\ref{fig:net}a).

We then measured real training loaders reading 512-cell minibatches into PyTorch from an object store whose bandwidth we
controlled (Fig.~\ref{fig:net}b). The \sone{} loader filled most of a 1\,Gbit/s link and delivered between thirty and a hundred times more
cells per second than AnnData's Zarr loader or TileDB-SOMA's loader for machine learning. Network latency matters as much as
bandwidth: every request waits a full round trip, and cloud storage adds tens of milliseconds to each. Because the \sone{}
index locates every block before any is read, the reader sends all of a minibatch's requests at once and keeps the next
minibatches' requests in flight. Our measurements showed that its original setting of eight concurrent requests left a
high-latency link mostly idle; with more requests in flight the rate recovered (Fig.~\ref{fig:net}c), and \texttt{singlet}
1.3.3 now uses these settings by default.

Finally, we read the files from a real cloud object store, Cloudflare R2, over the public internet (Fig.~\ref{fig:net}d).
With \sone, the first minibatch of a 580,000-cell lung atlas arrived in under a second, while downloading the AnnData file
first took well over a minute, and \sone{} then streamed cells tens of times faster than either Zarr layout. Because it
moves fewer bytes in fewer requests, a full epoch of random minibatches would cost about twenty times less in data-transfer
and request fees than with AnnData Zarr, at the prices of a provider that charges for both. \sone{} also needs no extra DataLoader worker processes to reach these rates,
since its decoder already uses every core (Supplementary Table~\ref{tab:workers}).

\subsection{Little room is left for any lossless format}
\label{sec:floor}

How much smaller could a file be? Following the payload of a matrix as ideas are added (Fig.~\ref{fig:floor}a), storing
the steps between entries and compressing them with the strongest general-purpose compressor shrinks the file a lot, but
modelling the counts, as \sone{} does, removes nearly a third of what is left. As a reference for what remains, we fitted count models of
the kind used for single-cell analysis, including negative binomial models and models that know each cell's cluster, on
half of each matrix's cells and measured how many bits they would need for the other half~\cite{hafemeister2019normalization,townes2019feature}.
Even though these models were charged nothing for their own parameters, the best of them was only a few percent shorter
than \sone. For data counted with molecular barcodes (UMIs), most of the remaining bits describe which molecules happened
to be captured, a random sample that no lossless format can avoid storing (Fig.~\ref{fig:floor}b). \sone{} is therefore
close to what count models of this kind allow.

\subsection{Using \sone}

\sone{} files are written and read by the open-source \texttt{singlet} package (Fig.~\ref{fig:eco}). One call stores a
matrix from AnnData, SciPy, SingleCellExperiment or Seurat, and one call loads it back as any of these, with exactly the
original counts, gene identifiers and barcodes; loading was faster than reading the equivalent AnnData or 10x file in both
Python and R (Supplementary Table~\ref{tab:eco}). For training, \texttt{singlet.torch.S1Cells} is a PyTorch dataset that
streams shuffled minibatches from a local path or a URL. Writing is fast as well, faster than gzip-compressed AnnData or
TileDB-SOMA, although the writer needs more memory than most (Supplementary Table~\ref{tab:writecost}).
