# Track A: accounting, container and entropy-coder tuning

Status: complete (all 14 corpus files, whole bundle). Result files are in `results/track_a_*`; tables between `<!-- TABLE_x -->` markers are regenerated by `python -P tools/track_a_notes.py`.
Everything here is reproducible from `bench/compression` with the tools named in each section
(`tools/track_a_*.py`, `harness/track_a_*.cpp`, codecs in `kernels/track_a.h`). All numbers are bytes unless a unit is given.
Machine: i7-1185G7, shared with three other agents, so **all timings are noisy** (CPU was at 100% from other processes
for most of the study); sizes are exact, speeds are min-of-3 and should be read as +-30%.

## 0. Findings in one page

1. **The matrix payload is a minority of today's bytes.** In the 14 corpus files the chunks hold 5-66% of the file
   (median 30%); row names, the row permutation and the redundant colsums/ptr blocks hold the rest. In the whole
   `GSE145370.singlet` bundle (187 MB, 70 matrices) **names (65.6%) + permutations (16.0%) + colsums and ptr blocks (1.2%) are 82.9% of the bytes**
   and the actual count payload (chunks) is 16.7%.
2. **Names are a function of (reference build, matrix kind)**: verified byte for byte (section 2). Moving them to a
   vocabulary model costs 1.7-2.5 MB per list once (xz) and 8 bytes per file. Best generic coder for them is xz-9e,
   41-43% smaller than zstd-3 (today); zstd-19/22 are in between; none of them gets near "free".
3. **Barcodes (colnames) are a random order of whitelist members** (100% of barcodes of all 14 files + the bundle are in the
   10x whitelist; the column order is uncorrelated with whitelist order). Sorting + delta coding does **not** pay
   (4.26 B/barcode vs 4.00 raw) because the original order has to be stored (ceil(log2 n) bits each); whitelist index
   costs 2.5-2.75 B/barcode (-37% vs 2-bit packing, -47% to -51% vs today's zstd-3) with a 3-6 KB model.
   If the pipeline emitted columns in whitelist order the cost would fall to 0.5-0.9 B/barcode.
4. **The row permutation is almost free to reconstruct.** The decoder can re-derive it from per-row nnz counts
   (identical permutation verified on all 14 files); counts cost 13-141 KB vs 720 KB-1.06 MB for the stored permutation
   and sit between -15% and +13% of their order-0 entropy. A *fixed* reference row order is much worse (+11% to +73% chunk bytes
   out of study) and no permutation at all costs +24% to +108% chunk bytes: the per-file frequency order is worth keeping, its
   *description* is what was wasteful.
5. **Entropy coder choice is worth a few percent only** (section 4): on the production prefilter bytes zstd-19 saves 2.6% of the chunk payload at the same decode speed, brotli-11 5.4% (decode +11-17%), xz 4.4% (decode +60-120%); a trained dictionary and the 128 MiB window add nothing worth a model slot; chunk_cols 256 -> 1024 -> 4096 -> whole matrix is worth about 3% / 2% / 2% each. The 8 bit planes of the low gap byte are 70-90% of the payload and nearly incompressible.
6. **The production reader is dominated by the per-column `std::sort`** on dense files (52% on tcell_5p) and by name
   parsing on sparse ones (86% on tumor_3p intron), not by zstd (section 5).
7. **Everything Track A can take out without touching the transform makes the 14 files 2.14x smaller** (114.4 -> 53.5 MB, 19.22 -> 8.99 bits/nnz; 0.07x on the sparsest, 0.68x on the densest): names and barcodes to models (-43%), permutation to row counts (-10%), ptr block derived. Section 7.
8. **Container-level byte identity is a property of the zstd version** (section 6): 10 of the 14 corpus files were
   written by zstd >= 1.5.7 and reproduce byte for byte with 1.5.7; tcell_5p, tumor_3p and all 70 matrices of
   the GSE145370 bundle were written by zstd 1.5.5/1.5.6 and reproduce with the 1.5.5 linked into the harness.

The codec summary table (every Track A codec on all 14 files, through `bin/bench.exe`) is in section 7.

- 2-bit packing in file order is 4 B/barcode and cannot be compressed further (zstd-19: 3.93-3.99).
- **Sorted 2-bit 16-mers + delta coding** (Rice-coded gaps, the sorted-set representation): the gap stream is 2.2-2.5 B/barcode, but the
  original column order must also be stored as a permutation of the sorted ranks (ceil(log2 n) bits = 1.9-2.1 B/barcode), so the total is 4.26-4.31 B: **worse than packing**.
  This is information theory, not tuning: a set costs log2 C(4^16, n) bits, an order costs log2 n! bits, and together they equal n*32 bits minus nothing.
- **Whitelist index** (fixed ceil(log2|W|) bits): 2.50 B/barcode (737K list, 20 bits) and 2.75 B (3.7M list, 22 bits); entropy bound within 3%.
  Model: 3,283 B (737K-august-2016) and 6,465 B (3M-february-2018): the whitelists are so regular that zstd-19 of the
  delta-coded sorted list is 3-6 KB.
- **If the column order were canonical** (sorted by whitelist index, e.g. fixed by the pipeline), the barcode set would cost log2 C(|W|, n):
  0.5-0.9 B/barcode, 3.3-4.5x less than the whitelist index. This is a format/pipeline recommendation (order is currently free information
  that costs ~1.6 B per barcode, 150 KB for pbmc_v2_shallow).
- bzip2 is the best generic coder on barcode text (3.3-3.9 B/barcode), which is a symptom of the whitelist structure.


## 3. Permutation

Tool: `harness/track_a_perm.cpp` (`results/track_a_perm.tsv`, `results/track_a_perm_check.txt`).
The writer sorts rows by descending nnz (counting sort, ties by ascending row id), stores the m-entry permutation (u32, zstd-3), and encodes
gaps in the permuted index space.

- **Re-derivation verified**: `perm_from_rnnz(rnnz)` in `kernels/track_a.h` equals the permutation stored in the original file for all 14 files
  (`results/track_a_perm_check.txt`); `a_perm_from_rowcounts` additionally passes the full matrix roundtrip (so the decoded chunks use the identical permutation).
- Row counts are coded as LEB128 varints (plain or zigzag-delta) with the best of zstd-19 / xz / brotli-11; the encoder tries all six and tags the winner.

Reading the sweep:
- **Levels.** On the production chunking, zstd-6 buys 0.7%, zstd-19 3.0%, zstd-22 nothing more; a 128 MiB window and long-distance
  matching add nothing (every chunk is < 1 MB, the window already covers it). The marginal cost is encode time: zstd-19 is 20-200x slower
  than zstd-3 (10 s per file), zstd-22 up to 10 s more, for the same decode speed.
- **Other coders.** brotli-11 is the best generic coder on these bytes: -6.6% (mean) vs zstd-3, up to -8% on the sparse files; xz -9e -5.7%.
  Both decode 10-50x slower than zstd (brotli 10-30 Mnnz/s, xz 1-6 Mnnz/s in the entropy stage alone) and brotli-11 encodes at ~0.1 MB/s
  (75 s for one file). bzip2 is worse than zstd-3 (+2.7%) and the slowest of all. The transform output is high-entropy byte-plane data,
  which LZ coders cannot model: the whole sweep spans 10%; the entropy coder is not where the bytes are.
- **Dictionaries** (ZDICT, trained out of study, 10 KB-1 MB): at level 3 a dictionary does not help (+0.4%: zstd's dictionary
  machinery costs more in the frame than it saves on 64-600 KB inputs with this much entropy); at level 19 it is worth 0.5% over plain
  zstd-19 (0.965 vs 0.970) and 2-4% on the two smallest files (tumor_3p: 0.961 / 0.977 vs 0.974 / 0.979), where the per-chunk
  "learning" cost of zstd is largest. fastCover selected k=50, d=6 for every sample, the dictionaries are mostly varint-metadata and
  bit-plane fragments. Not worth a model slot.
- **Chunk size** (table d): bigger chunks compress better for every coder, because each chunk restarts the LZ state and the varint
  metadata / bit-plane statistics are learned again: 256 -> 1024 -> 4096 -> whole matrix gives about -3% / -2.5% / -2% (zstd-3) per step,
  so whole-matrix zstd-3 is already as small as per-chunk zstd-19, and whole-matrix xz/brotli reach -8 to -10% vs today. The price is
  random access: 1024 columns per chunk means the Python reader's "one column in 10 us" claim holds for a 100-600 KB decompress, whereas
  whole-file chunks require decoding everything. The coder-independent decode work does not depend on chunk size (last column; the
  noise there is the shared machine, not an effect).
- **Where the bits are** (table e): the 8 bit planes of the low gap byte are 70-90% of the compressed payload (they are nearly
  incompressible: zstd-19 gets 0-5% on them), the upper gap bytes 5-25% and the varint metadata (per-column group count, value, run
  length) 2-10%. Compressing the three streams separately is within +-1% of compressing them jointly, i.e. zstd finds no cross-stream
  structure. Anything that wants more than ~7% has to change the transform (Track B) or model the gaps (Track C), not the coder.

- **Dense file (tcell_5p exon, 10.5 M nnz, 152 nnz/column): the per-column `std::sort` is 52% of the decode time (133 ns/nnz)**;
  the VOCSC inverse transforms (bitmap_unpack 24 ns/nnz, bit_planes_decode 27 ns/nnz, both bit-at-a-time scalar loops) are 20%, zstd
  itself is 2.6% (6.6 ns/nnz) and names 12%. The sort exists because the writer groups each column's entries by value and the reader
  must restore ascending row order after un-permuting; it is O(k log k) per column with a 64-bit pair comparator and dominates as soon
  as columns have more than a few dozen entries. Total 237 ns/nnz = 4.2 Mnnz/s (2.5 s for the file).
- **Sparse file (tumor_3p intron, 0.11 M nnz, 4 nnz/column): 90% of the time is the metadata block: zstd decode of the 15 MB name TLV
  (42%) and splitting it into 297k `std::string`s (47%)**; the matrix itself is 3% of the time. 2.3 us/nnz = 0.4 Mnnz/s. This is also
  the pbmc_v2_typical / brain picture in between (names 36% / 19%, sort 38% / 44%).
- Ranking for the reader: (1) avoid the per-column sort (write rows in ascending row order within the column with the value as a parallel
  stream, or sort by value stably so the permuted order is monotone within groups and merge k sorted runs); (2) replace the bit-at-a-time
  `bit_planes_decode` and `bitmap_unpack` with byte-at-a-time / pdep versions (both are >= 24 ns/nnz for a few bytes of work); (3) make
  names lazy (the vocabulary id of section 2 makes the metadata block disappear and turns the sparse-file decode from 243 ms into ~25 ms);
  (4) the whole-file CRC32 (1-3%) and the chunk CRCs (1%) are the only verification costs, and the zstd checksum already duplicates the chunk CRC.
- Track B's rANS/bitmap kernels are measured against the *payload-only* ceiling: the coder-independent work here is 24-50 ns/nnz with
  the sort and ~8-10 ns/nnz without it; zstd-3 entropy decoding is 5-10 ns/nnz. A 200 Mnnz/s target means <= 5 ns/nnz for everything.

## 7. Codec table (bench harness, all 14 files)

`./bin/bench.exe --codec ref_1pz_v1_L3,a_names_as_model,a_perm_from_rowcounts,a_names_perm_model,a_vocsc_zstd19,a_vocsc_zstd22long,a_vocsc_xz,a_vocsc_brotli,a_vocsc_zstd_dict --no-file-check --out results/track_a_run.tsv corpus/*/exon_counts.1pz corpus/*/intron_counts.1pz`

- `a_names_as_model`: matrix payload, permutation, ptr block exactly as production (zstd-3, 1024 cols/chunk); row names replaced by an
  8-byte vocabulary id (model `results/track_a_vocab_<build>.bin`), barcodes in the cheapest of {inline zstd-19, 2-bit packed, whitelist index,
  sorted Rice deltas + order} (always the whitelist index here; model `results/track_a_whitelist_*.bin`), user kv as production.
- `a_perm_from_rowcounts`: production everything, except the permutation block is replaced by the per-row nnz counts (varint, best of
  plain/delta x zstd-19/xz/brotli) and the decoder re-derives the counting sort.
- `a_names_perm_model`: both of the above plus no ptr block (column lengths derived from the chunk metadata) = everything Track A can remove
  without touching the transform.
- `a_vocsc_zstd19`, `a_vocsc_zstd22long` (level 22, windowLog 27, long-distance matching), `a_vocsc_xz` (-9e), `a_vocsc_brotli` (11, w24),

What the run says:
- **Total size.** Taking the names to a vocabulary and the barcodes to whitelist indices is **-43%** over the 14 files (114.4 -> 65.0 MB; -75% on tumor_3p intron, -27% on
  brain_sn_v3_intronic intron); re-deriving the permutation from row counts alone is -10%; with both, plus dropping the redundant ptr block, the 14 files go from 19.22 to
  **8.99 bits/nnz (0.468x, 2.14x smaller)**, from 0.07x (tumor_3p intron: 4,040,778 -> 283,775 B, 301 -> 21 bits/nnz) to 0.68x (tcell_5p exon: 13.76 -> 9.39 MB). The model
  files (8.05 MB for both species' exon+intron lists, 10 KB of whitelists) are less than one average input file; charging them entirely to these 14 files still gives 0.54x.
  This is a **lossless** change of the container only: payload bytes are identical to the production writer's (table 7.1, "payload vs zstd-3 = 1.000").
- **Entropy coder.** Swapping the coder on the unchanged transform saves 1.6% (zstd-19/22) to 2.9% (brotli-11) of the *total* file, or 2.6% / 5.4% of the chunk payload; a trained
  dictionary buys another ~0.5 percentage points over zstd-19 on the 10 files that have out-of-study training data, and the huge window / long-distance matching nothing.
  Decode cost: zstd-19, zstd-22 and zstd+dict decode exactly as fast as zstd-3 (the entropy stage is 13-30 cycles/nnz of 640-850 on the dense files, 2-4%);
  brotli adds 100-220 cycles/nnz (+11% / +14% / +17% of the whole decode on tcell_5p / pbmc_v2_typical / pbmc_v2_shallow exon); xz adds 480-1160 cycles/nnz (+71% / +59% / +122%) and bzip2 more than xz.
  So the free lunch is zstd-19 at write time (-2.6% payload, same decode speed, 20-200x the encode time) and the only coder that pays for its decode cost is brotli on files that are read rarely.
- **Decode of the model-side codecs.** On dense files nothing changes (658 / 643 vs 692 cycles/nnz; names are 5-12% of a dense decode); on sparse files the decode halves
  (tumor_3p intron 7214 -> 3812 cycles/nnz) because the 15 MB name TLV is neither decompressed nor parsed; what is left there is materialising 272k `std::string`s from the vocabulary
  (a lazy name view would remove that too). Re-deriving the permutation costs about 5% of the sparse decode and nothing measurable on dense files.


## 8. What the other tracks should know

- **Baselines to beat, payload only** (chunk bytes, no names / permutation / ptr / colsums, chunk_cols 1024; section 4 table a):
  zstd-3 as today 6.81 bits/nnz on pbmc_v2_typical exon, 11.91 tumor_3p exon, 14.31 tumor_3p intron, 8.54 pbmc_v3_lowgenes intron;
  the best entropy coder on the unchanged transform is brotli-11 at 0.934x of that, whole-matrix xz at ~0.90x. Anything claiming
  more than ~10% over today must come from a different transform or a model, and should be reported against these payload numbers,
  not against the file size (which is 50-90% names and permutation).
- **Reusable code in `kernels/track_a.h`** (namespace `cs::ta`): `prepare(M, chunk_cols)` = the writer's exact prefilter bytes per chunk
  (verified byte-identical); `decode_chunks()` = the reader's chunk loop with a pluggable entropy decoder; `ec_compress/ec_decompress`
  for zstd (level/window/LDM/dictionary), xz, brotli, bzip2; `Models::get()` loads the vocabulary / whitelist models and
  `enc_names_model / dec_names_model` give any codec the same model-side names at the same cost, so cross-track totals are comparable;
  `perm_from_rnnz` reproduces the writer's permutation; `BitW/BitR` bit IO; `bc_code/bc_str` 2-bit barcodes.
- **Keep the per-file frequency row order** (section 3): identity (vocabulary) order costs +24% to +108% chunk bytes with the current
  transform, a fixed cross-study order +11% to +73%. Its description is 13-141 KB as row counts. Any new index coder should be measured
  with and without the permutation before the permutation is declared unnecessary. The counts are also free model context (row
  frequency bucket per gap) because the decoder has them before the first chunk.
- **Column order is free to change**: the barcode order carries no information (pipeline first-seen order); a codec that reorders
  columns pays ceil(log2 n) bits per column (~2 B/column, 30-200 KB per file) to restore it, or nothing if the format canonicalises to
  whitelist order (then the barcodes themselves drop to 0.5-0.9 B each).
- **Speed ceiling of the current reader** (section 5): 237 ns/nnz on the dense file of which the per-column sort is 133 and the
  bit-plane / bitmap inverses 51; zstd-3 is 7. The bit-plane transform costs 25-30 ns/nnz to undo and earns about 5% (table e: the
  planes are 70-90% of the payload and nearly incompressible); a format without it would decode faster and lose little.
- **Metadata block decode is 240-340 ms per file regardless of size** (zstd of 15 MB of names + 300k string allocations); in sparse
  files that is 90% of the read. The vocabulary id removes it entirely; so does lazy name decoding.
- **File identity vs matrix identity** (section 6): a re-emitted `.1pz` is byte-identical only with the writer's zstd version
  (1.5.5/1.5.6 for the bundle and 4 corpus files, 1.5.7 for 10 corpus files); all roundtrip claims in this study are on the canonical matrix.
- **Second-pass compressibility of today's files** (for Track D): the chunk payload re-compresses by 3% (zstd-19) to 7% (brotli-11),
  the name block by 35-40% (xz), the permutation block by 0% as bytes but 90%+ as information (counts instead of a permutation).
