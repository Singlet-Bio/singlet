## 0. Summary and H3 verdict

H3 as stated in `notes/brainstorm_fable.md`: (i) H(interval | gene, count) < 1 bit per UMI; (ii) I(exon; intron) per
intron nonzero > 0.3 bits for snRNA.

**Verdict.** (i) is *partly supported*: exon matrices, 0.41-0.87 bits/UMI as an exact multiset in-sample for 5 of 7
samples (1.10-1.12 for brain_sn_v3_deep and tumor_3p), and 0.46-0.90 bits/UMI actually coded by the adaptive,
model-free split for 5 of 7 (1.15 brain_sn_v3_deep, 1.55 tumor_3p); *falsified* for all 7 intron matrices (1.9-2.4
bits/UMI in-sample iid, 1.89-1.99 as multiset, 1.94-2.29 coded; the one exception to the range is the tiny tumor_3p,
1.21 / 1.19 in-sample because its 107k UMIs overfit any per-gene table, 1.96 coded). (ii) is *falsified* for snRNA: with the gene's rate
class and the cell's depth already in the context, the exon count of the same gene adds 0.106 (brain_sn_v3_deep) and
0.057 (brain_sn_v3_intronic) bits per intron gene-nonzero (cross-validated), and the real conditional codec saves 0.080
and 0.045 bits per intron nonzero (1.1 % and 0.6 % of the intron payload). Only tcell_5p (0.39) and the tiny tumor_3p
(0.80) pass 0.3, and neither is snRNA. The raw (unconditioned) MI is 1.0 and 0.23 bits per intron gene-nonzero for the two
snRNA samples, but almost all of it is explained by gene expression level and cell depth.

**(i) is supported for exon matrices of ordinary 3' libraries and falsified otherwise.** In-sample, with a static
per-gene interval table, the interval choice costs 0.51 / 0.65 / 0.66 bits per UMI for pbmc_v2_typical, pbmc_v2_shallow
and brain_sn_v3_intronic exon, but 1.08-1.26 for tcell_5p (5' chemistry), pbmc_v3_lowgenes, tumor_3p and
brain_sn_v3_deep exon, and 1.2-2.4 bits per UMI for every intron matrix (intron UMIs spread over ~20 intervals per gene
with only weak positional bias). Conditioning on the (cell, gene) UMI count bucket changes this by < 0.04 bits: the
count does not predict the interval; the gene does. The honest, self-contained number (adaptive Dirichlet-multinomial,
no table transmitted, no model) is within 0.05-0.1 bits/UMI of the in-sample static table for exon and *better* than
it for intron, so the split layer needs no shipped model at all. Per interval nonzero the split costs 0.7-1.7 bits
(exon) and 2.2-3.0 bits (intron), i.e. 10-30 % (exon) and 17-41 % (intron) of the whole payload.

**(ii) is falsified in the sense that matters for a codec, and the sign of the protocol effect is the opposite of the
expectation.** The raw mutual information between "gene has exon UMIs in this cell" and "gene has intron UMIs in this
cell" is 1.0 bits per intron gene-nonzero for brain_sn_v3_deep but only 0.23 for brain_sn_v3_intronic; once the
intron presence model already conditions on the gene's rate class and the cell's depth bucket (which any competent
codec does), the *additional* information from the exon count of the same gene is 0.11 and 0.06 bits per intron
gene-nonzero for the two snRNA samples, 0.05-0.17 for PBMC, 0.42 for tcell_5p and 0.96 for the tiny tumor_3p. The
reason: although P(intron present | exon present) is 20-200x P(intron present | exon absent), only 4 % (brain_sn_v3_
intronic) to 38 % (pbmc_v3_lowgenes) of intron gene-nonzeros have exon UMIs of the same gene in the same cell; in
nuclei the intron matrix is the *dominant* signal and the exon matrix is too sparse to predict it. Depth coupling
(k_intron from k_exon) adds nothing over the per-cell delta coding the harness already does.

What the factorisation is worth as a codec (idea3_gene_then_interval, range coder, integer decode path, rate-class
tables transmitted in the stream (6 bits/gene + a 64 x 24 table), no shipped model; all 14 files verified
decode(encode(M)) == M): 5.81 / 8.40 / 10.42 / 13.30 / 5.54 bits per interval nonzero on pbmc_v2_typical exon /
intron, tumor_3p exon / intron, pbmc_v3_lowgenes exon, and **9-27 % below today's zstd-3 VOCSC payload on
every one of the 14 files** (exon -14 to -27 %, intron -9 to -21 %; section 8), matching the measured cross-entropies
to within 0.1 bits. The same machinery applied directly at interval level (every row its own "gene") is 0.03-0.24
bits/nnz worse in-sample (and 0.14 better on one intron file, pbmc_v3_lowgenes); the factorisation's real advantage
is out of sample (section A3: gene tables transfer across studies, interval tables do not) and model size (38-78k
genes instead of 310-386k rows). Out-of-sample tables (2-4 MB, pooled over the other studies of the build; static
split or adaptive split from the pooled prior) are *worse than the self-described tables on all 8 files tried*
(+0.3 to +5.5 bits/nnz static, +0.2 to +4.4 with the adaptive split) and, with the static split, worse than today's
zstd payload on 5 of 8 (2 of 8 with the adaptive split); self-description wins because the per-gene rate class costs
17-50 kB while the cross-study / cross-chemistry mismatch costs 3-100 %.
The exon -> intron codec (section 6) saves 0.035-0.155 bits per intron nonzero (0.4-1.3 % of the intron payload) on
PBMC, 0.08 on brain_sn_v3_deep, 0.39 on tcell_5p and 0.80 on tumor_3p (6 % of the intron payload, 2.2 % of the joint
payload): H3(ii) is falsified for nuclei.

## 1. Data facts that drive everything (A1)

Rows are exon / intron intervals, contiguous by gene in every file; the gene id is the prefix of the row name, so the
decoder recovers the grouping from the names it already has (or from the vocabulary id, Track A). Human: 38,606
exon genes over 310,797 intervals (8.1 per gene, median 4, p90 19, max 368); mouse: 78,298 over 386,028 (4.9, median
2). UMI-weighted, an exon UMI falls in a gene with 6.5-10.7 intervals, an intron UMI in a gene with 15-20. 12-43 % of
exon UMIs are in single-interval genes (nothing to split); 1-8 % of intron UMIs. The interval level has only 0.3-35 %
more nonzeros than the gene level (nnz_int / nnz_gene = 1.003-1.35): almost every (cell, gene) pair touches one
interval, so "which interval" is a per-pair choice among the gene's intervals, not a per-UMI one.

## 2. Interval choice given gene (A2)

Measured as the empirical entropy of the interval distribution of each gene's UMIs (static, in-sample, table not paid
for), then as what a codec can actually achieve: the exact multiset code (order of UMIs inside a gene is not
information), with out-of-sample static tables (pooled over the other studies of the same reference build; and the
single best other sample as an oracle upper bound on "ship a table"), with a zero-shot length-proportional prior, and
adaptively (Dirichlet-multinomial with integer pseudo-counts updated as the file is decoded, flat or best-sample
prior).

Findings:
- Count-bucket conditioning (c = 1 / 2 / 3-4 / 5+) gains < 0.04 bits/UMI. The per-bucket entropies do fall with c
  (exon c=1: 0.7-1.5 bits, c>=5: 0.0-0.6) because multi-UMI pairs sit in the dominant 3' interval, but the buckets are
  predictable from the gene alone.
- Shipped interval tables do not transfer: pooled tables cost 1.3-2.7 bits/UMI vs 0.5-1.3 in-sample for exon. Interval
  usage is protocol specific (3' v2 vs v3 vs 5' end bias, nuclei vs cells); the best single other sample is a
  same-chemistry sample (h_c, 10x v3, for most human files) and still loses 0.05-1.2 bits/UMI.
- The adaptive split from a flat prior is within 0.05-0.1 bits/UMI of the optimistic in-sample static number for
  exon and matches or beats it for intron, with nothing transmitted and no model. An out-of-sample prior on top adds
  0.00-0.09 bits/UMI. Interval length as a prior is useless (1.3-3.1 bits/UMI).
- Why not transmit the table (the "310k x 1 byte" of the brainstorm): 8 bits per interval is 2.5 Mbit for the 310,797
  human exon intervals, against 0.23 Mbit of total learning cost for the adaptive split on pbmc_v2_typical exon
  (2.16 Mbit adaptive vs 1.93 Mbit exact-multiset in-sample, 4.68 M UMIs); over all 14 matrices the learning cost is
  0.04-0.49 Mbit against 2.2-3.1 Mbit for a one-byte-per-interval table, so adaptive beats a transmitted table by
  4-70x, and an unused interval costs nothing (flat pseudo-counts).

## 3. Gene-level vs interval-level model (A3, A4)

The same presence x depth-bucket + count model evaluated at both levels (cross-entropies, 64 rate classes, class x
bucket tables; "side" counts the per-gene class list and the tables when they are transmitted). In-sample the two
levels tie to within 0.15 bits/nnz: the split layer costs almost exactly the extra presence bits the flat model spends
on 8x more features. Out of sample the gene level wins by 0.3-1.8 bits/nnz with pooled tables and 0.1-2.2 with the best
single sample, because the gene-level presence tables transfer across studies while interval tables encode the
protocol. Both in-sample variants beat today's chunk payload by 0.9-2.0 bits/nnz; out-of-sample pooled tables are
often *worse* than today's zstd (cross-study heterogeneity is larger than the gain from a per-feature model;
Track C / Ideas 1-2-4 attack that with depth-aware and adaptive models, which is out of scope here).

Where the bits go (A4): "which gene" is 40-70 % of the factorised payload (2.3-9.5 bits/nnz), "which interval"
10-30 % for exon and 17-41 % for intron (0.7-3.0 bits/nnz), "how many" 0.06-1.45 bits/nnz. For question C
(gene-level container + interval-split layer): yes, the split layer is a separable 10-40 % of the payload that needs
no model and could be stored as its own stream, letting gene-level consumers skip it.

## 4. Exon -> intron (B1)

Per cell and gene, 2-fold cross-validated by cell parity so context-count bias is removed. Conditioning the intron
presence on the exon count bucket of the same gene in the same cell saves 0.05-0.17 bits per intron gene-nonzero for
PBMC, 0.06-0.11 for the two snRNA brain samples, 0.42 for tcell_5p and 0.96 for tumor_3p (the smallest, sparsest
file). Count-given-presence gains < 0.01 bits from the exon bucket. Predicting the per-cell intron gene count from the
exon count is no better than the delta against the previous cell. The joint codec (section 6) is therefore expected
to save 0.5-2 % of the intron payload for brain and PBMC and ~10 % for tumor_3p.

## 5. A codec: idea3_gene_then_interval (kernels/idea3.h, idea3_codec.h, harness/idea3_bench.cpp)

Per cell: k = number of genes present (zigzag delta vs previous cell, adaptive bit-length symbol + raw offset) ->
the k-subset of genes by bisection with exact window probabilities from integer prefix sums of -log2(1 - p[b][g])
(O(k log G) binary decisions, Idea 1's survival trick, all integer: 2^-44 fixed-point logs, 2^-48 fixed-point
1 - 2^-x via a 4096-entry table) -> UMI count per gene (adaptive 17-symbol model, context = gene rate class x depth
bucket) -> split of the c UMIs over the gene's intervals as an exact multiset by a Beta-binomial chain with adaptive
integer pseudo-counts (static 16-bit frequencies when c = 1). Presence probabilities: per-gene rate quantised to 64
classes, class x 24 depth buckets table transmitted (self-described variant) or taken from an out-of-sample model
(`*_oos` variants, leave-one-study-out pools in `results/idea3_pools.tsv`). The row/col names and user_kv are
zstd-9 separately and reported apart (Track A owns names). Decoder is integer-only; the only floating point is in
building constant tables at start-up and in encoder-side bit accounting.

Verified: decode(encode(M)) == M (indptr, indices, data, row and column names, user_kv) on all 14 corpus files for
`idea3_gene_then_interval` and `idea3_interval_direct`, and on 8 files for the two `*_oos` variants (28 + 16 runs, zero
failures; file-level re-emission of the original `.1pz` was not checked, the canonical matrix is the object of study).
Payload matches the A3 cross-entropy prediction within 0.1 bits/nnz (e.g. pbmc_v2_typical exon: 5.81 coded vs 5.88
predicted; the C++ count model uses finer contexts (class x depth bucket, 1.11 vs 1.17 bits per gene nonzero) than the
Python estimate, which more than pays for the 16-bit quantisation of the presence codes, the warm-up of the adaptive
count/split models and the range-coder overhead). Speed is not competitive and was not the goal of this track: decode 0.14-0.72 Mnnz/s of CPU time
(single thread, i7-1185G7 shared with seven other agents; the first version measured 0.05-0.25 Mnnz/s wall on a
loaded machine). The cost is ~15 binary range-coder decisions per gene nonzero, each with an integer 1 - 2^-x
evaluation and a 64-bit division. A production version would use Idea 1's table-driven CDF search for presence and a
static or per-gene-quantised split table; none of that changes the bit counts.

## 6. B codec: intron | exon (kernels/idea3_joint.h, harness/idea3_joint.cpp)

Exon coded with the A codec; intron coded with the same machinery except that for every gene with exon UMIs in the
cell (and with introns) one binary decision P(intron present | gene class, depth bucket (12 coarse), exon bucket in {1,
2-3, 4+}) is coded first, then the remaining intron genes are coded by bisection over the non-exon genes with window
probabilities that exclude them (P(present | e = 0) tables, class x 24 buckets); counts keep the A contexts (the exon
bucket gave < 0.01 bit/nnz). The decoder uses the *decoded* exon matrix. Side info: intron class list + the two
tables, 0.02-0.9 bits per intron nnz. Both matrices of every sample are decoded and compared with the originals
(7 samples, zero failures). Results in `results/idea3_joint.tsv` and table C3 below: conditioning saves 0.035-0.155
bits per intron nonzero on the PBMC samples, 0.045 / 0.080 (brain_sn_v3_intronic / brain_sn_v3_deep), 0.39 (tcell_5p)
and 0.80 (tumor_3p); i.e. 0.4-1.3 % of the intron payload for everything except tcell_5p (3.9 %) and tumor_3p
(6.0 %), and 0.2-0.6 % of the joint exon + intron payload (2.2 % for tumor_3p). The codec realises 64-96 % of the
cross-validated gene-level prediction of section 4 (per intron nonzero: 0.049/0.173/0.059/0.414/0.952/0.083/0.048
predicted vs 0.035/0.155/0.038/0.394/0.798/0.080/0.045 coded, in the sample order of table C3). Using richer gene context (the exon-side rate class of the
gene) in the Python estimate adds only 0.02-0.12 bits more (brain_sn_v3_deep 0.106 -> 0.126, tcell_5p 0.42 -> 0.54).
`idea3_joint_intron_nocond` (same code path, exon information withheld) costs 0.04-0.3 % more than the independent
codec (1.2 % for tumor_3p, whose extra side tables are not amortised), i.e. the structure itself is nearly free.

## 7. Three insights for the format redesign

1. Store gene-level counts as the primary container and the interval split as a separable, self-describing layer:
   the split is 10-40 % of the matrix payload, needs no shipped model (adaptive integer pseudo-counts match static
   in-sample tables), is skipped entirely by gene-level consumers, and makes the learned/shipped model 8x smaller
   (38-78k genes instead of 310-386k rows) with *better* out-of-sample transfer.
2. Describe the file to itself instead of shipping tables: a 6-bit rate class per gene plus a 64 x 24 class x depth table
   costs 0.01-0.4 bits/nnz (17-50 kB; more only for the tiny files) and beat 2-4 MB out-of-sample presence tables on all
   8 files tried by 0.3-5.5 bits/nnz (the out-of-sample versions were worse than today's zstd payload on 5 of 8). Never
   ship interval tables or any 5'/3'-position prior: interval usage is chemistry specific (pooled tables cost 2-3x the
   in-sample bits per UMI). Ship, at most, priors that an adaptive model corrects (an oos prior under the adaptive split
   gains 0.00-0.09 bits/UMI).
3. Do not spend effort on cross-matrix (exon | intron) conditioning: after depth and gene rate it is worth
   0.05-0.17 bits per intron nonzero on real libraries and least of all on nuclei, because the two matrices rarely
   touch the same (cell, gene). The columns are shared, so the barcode list and the cell order should be stored once
   per sample (that is where the shared structure actually is), not the counts.
