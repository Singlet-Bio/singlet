# E4: tiered container, derived members, and transfer latency

Status: complete, 2026-10-22. Plan: `plans/E4_tiered_container_derived_members.md`. Measurement only; the production
writers were not touched. Everything below is reproducible from `bench/compression` (section 7). Machine shared with
nine other agents; timings of the tools are therefore not interesting, sizes are exact.

## 0. Findings in one page

1. **78% of a sample's bytes are derivable.** In the 187 MB bundle `GSE145370.singlet` (14 samples, 13.3 MB per sample on
   average) 10.39 MB per sample (69-84% across samples) can be regenerated from the reference build and from other
   members: the whole `splice_psi.1pz` (1.76 MB, 13.2%), the feature names of exon/intron/vdj (6.28 MB, 47.1%), the
   row permutation net of the row counts that regenerate it (1.75 MB, 13.1%), three of four duplicate barcode lists
   (0.45 MB, 3.4%), ptr and colsums (0.14 MB, 1.0%), and all of `cell_calls.tsv` but the called set (22 KB). What is left
   is the count payload (exon, intron, sj, vdj), the sj junction list, one barcode list, the called set and the run
   metadata.
2. **Recomputation was actually carried out and is exact.** colsums, ptr and perm: 70/70 matrices. `splice_psi.1pz`:
   regenerated from `sj_counts.1pz` alone, **file bytes identical on 14/14 samples (24,575,390 B)**, float32 PSI
   bit-identical (0 ulp) to the production `compute_psi()` on 4,664,595 entries. `cell_calls.tsv`: byte-identical on
   21/21 samples from (called set, exon column sums). `summary.json`: 17 numeric fields x 14 samples + 5 fields x 7
   corpus samples = 273/273 reproduced; `pileup_stats.json` and `provenance.json` matrix-sum fields 112/112.
3. **Zero-cost today / zero-cost if pinned / independent.** Zero-cost today: colsums, ptr, perm, duplicate name lists,
   splice_psi (as shipped), cell_calls except the called set, 15 of the 34 numeric scalars in summary.json, the matrix-sum
   fields of pileup_stats and provenance, the sha-256s of manifest.json. Zero-cost *if the format pins the formula*: the
   float PSI (the shipped file is not the float, see surprise 1), `log10_umi` (libm), the upper-median and 6-digit
   printing rules, the rowname-prefix gene map. Independent: the four count matrices, the sj junction list, the called set
   (but only 54-3,284 B once column depth is known), STAR read counts, run metadata, read-level counters. **vdj is
   independent** (16% of its entries equal the exon-count sum of the same gene; its total UMIs are 7.0-9.5x those exon counts).
4. **Cells-first transfer, brain_sn_v3_deep (exon + intron, 3,288 nuclei of 84,424 columns).** Today's best reader needs
   13.98 MB / 1.27 s (100 Mbit/s, 50 ms RTT, 3 rounds) for the first 1024 cells and 18.64 MB / 1.64 s for all called cells;
   everything is 25.05 MB / 2.10 s. Proposed layout (estimate iii): 3.42 MB / 0.37 s, 6.69 MB / 0.64 s, 13.29 MB / 1.16 s, all in
   2 rounds. At 1 Gbit/s 0.26 -> 0.13 s, 0.30 -> 0.15 s, 0.30 -> 0.21 s. Exon alone is 2.84 MB for all called cells.
   Across the 7 corpus samples all-cells transfer falls 2.3-22x in bytes (tumor_3p 8.8 -> 0.40 MB) and first-chunk time at
   100 Mbit/s falls 0.82-1.27 s -> 0.12-0.37 s.
5. **Where the gain comes from is not what the plan assumed** (surprise 2). Of the all-cells saving, removing names,
   permutation, ptr and colsums and putting the chunk index first is 79-97% (86% on brain_sn_v3_deep); separating empties into
   their own member is 1-15% (it shrinks the transfer by 4-14% where empties are a thin tail, by 25-40% where they are mixed
   in: pbmc_v2_shallow, tumor_3p); the payload codec is 0-11%. For "everything", tiering costs nothing.

### Surprises

1. **The shipped `splice_psi.1pz` does not contain PSI.** Its values are {0, 1}: `round-half-even(PSI)` (89-97% of entries
   are PSI = 1.0 exactly, 1 means PSI > 0.5, PSI = 0.5 is stored as 0). The repository writer (`pz_writer.h:615`,
   `static_cast<uint32_t>`) would truncate instead and differs from the shipped values in 56,947 of 4.66 M entries (0.45-3.0%
   per sample), so the shipped bytes were not produced by exactly this code path; the rint variant reproduces all 14 files byte
   for byte. Anyone reading `bundle.splice_psi()` as fractions gets a binary indicator. (This is a data-quality issue
   outside E4; I did not touch it.)
2. **Today's files are already roughly depth-sorted**: called cells sit in the first 1.05-1.54x n_called columns (tumor_3p:
   3.9x), so the cells are in the first 5-63 chunks of 15-95 and a reader that knows this does not have to download the
   empties. The cost of selective reads today is the metadata block (names, 3.4-4.6 MB) at the *end* of each file and the
   chunk table that sits *behind* the 0.7-1.1 MB permutation block.
3. **cell_calls.tsv never contains an EmptyDrops result.** In 21/21 samples it lists called cells only, `is_cell` is TRUE,
   the p-value column is the sentinel `0.0000e+00` and the method is `star_solo`. The file is a barcode list plus a function
   of the matrix.
4. The brief's "cells-first 3-5 MB" holds for exon only (2.84 MB for brain_sn_v3_deep); the intron matrix of nuclei has
   4.7 M nonzeros in 3,288 cells, so exon + intron is 6.7 MB.
5. Only `sj_counts` colsums frames differ between zstd 1.5.7 and 1.5.5 (5 of 14); the other 65 are identical in both. Frame
   bytes, unlike the decoded arrays, are a property of the zstd build.
6. `compute_psi()`'s comment says donor events take priority; the code takes the first event in bytewise-sorted event-id order.
   They disagree on 1 of 9,293 junctions in GSM4317429 (and on any junction where the strings sort the other way). Pin the code.

### 2.3 Findings per artifact

**splice_psi.** Definition (`splice_psi.h`): junction names `chrom:start-end`; a donor group `chrom:start-D` or acceptor
group `chrom:end-A` with at least two junctions is an event; a junction belongs to the first event in bytewise-sorted
event-id order; PSI = float(count) / float(sum of the counts of the junctions of the event in that cell). Sums are integers
below 2^24 and IEEE division is correctly rounded, so summation order and library version do not matter: numpy float32 is
bit-identical to the C++ on every entry. The shipped member stores `rint(PSI)` as uint8 (vt 1), so it carries one bit per
entry that is itself a function of the sj counts. GSM4317429 has 372,571 entries, 89% with PSI exactly 1.0. Inputs are the sj matrix
with its row names only; no reference needed.

**colsums, ptr, perm.** colsums is never read by `pz_reader.h`. ptr is required by the reader but equals the per-column
sum of the value-group counts in the chunk metadata. perm is the counting sort of per-row nnz; Track A's roundtrip showed the
decoder can regenerate it.

**cell_calls.tsv.** Rows are the called barcodes in bytewise-sorted order (STAR's `filtered/barcodes.tsv` order), all
`TRUE`, `0.0000e+00`, `star_solo`; `log10_umi` is `%.4f` of log10 of the exon column sum (`bc_totals`). Python's and numpy's
log10 agree with the pipeline's glibc on all 127,105 rows. The only independent content is *which* columns are called
(`export.h:486-540` copies STARsolo's EmptyDrops_CR result, computed from the whole-whitelist raw matrix that is not in the
bundle). Given each column's total UMI the called flag costs 54-3,284 B per sample at its ideal adaptive code length (half-octave
depth bins, MDL parameter cost), against 1.9-12.1 KB for a raw bitmap and 22 KB for the deflated TSV; a single UMI
threshold mispredicts 0.07-3.8% of columns, so the exception list is 20-1,444 B. Idea 2 independently found ~0.02 bits/column.

**summary.json** (34 numeric scalars). 11 are functions of the matrices and pileup_stats (n cells, estimated cells, both
medians, median genes, genes detected, fraction in cells, mean reads per cell, exonic, intronic, intergenic fractions); 4 are
functions of the two STAR read counts (mapping rate, percent, and the duplicate copies `total_reads`, `mapped_reads`); all 15
reproduced exactly, printed with C++ `ostream` default (`%.6g`). Pinned rules: upper median `v[n/2]` of the called-cell exon
column sums; gene = rowname prefix before the first `_` (`bundle.py:1713, 1873` use the same); fraction = in-cell UMI / all UMI over
all columns; exonic = `exon_hits / pileup mapped_reads`. 3 are constants never computed (`sequencing_saturation`,
`median_mito_fraction`, `exit_code`); 8 are block counters that are zero here (independent in general); 8 are run metadata
(`n_input_reads`, `n_uniquely_mapped`, `peak_rss_gb`, `wall_seconds`, `star/pileup/export_seconds`, `protocol_id`). The three
JSON members are 1.6 KB per sample deflated, 0.012% of the bundle; their derivation matters for hygiene, not for bytes.

**vdj_gene_usage.** Counts reads whose aligned span overlaps a VDJ gene span (spliced reads count over their introns), first
hit wins, deduplicated per (cell, gene, UMI). Against the exon matrix: 16% of nonzeros equal the exon-count sum of rows with
the same symbol (GSM4317423 15.8%, GSM4317429 16.6%), 99.99% are >= it, 76% have no exon count at all, and the totals are
494,636 vs 70,849 and 714,667 vs 75,105 UMIs. Independent.

**mt_heteroplasmy.** All 14 members are 0x0 stubs (151 B). The scaled-VAF writer (`export.h:1172-1180`) is deterministic
in the allele counts, which are not a bundle member, so a non-empty member would be independent here. No such member exists
in the corpus, so this was not tested.

## 3. Part B: tiered layout and latency

### 3.1 What the shipped files look like (this changed the model)

Layout of a `.1pz`: header (96 B), permutation, ptr, **chunk table**, chunks, colsums, **metadata (rownames and colnames in
one zstd frame)**. So a reader needs 0.7-1.1 MB of permutation/ptr before it can even read the chunk table, and 3.4-4.6 MB of
names to learn a single barcode. The columns are in a noisy depth order (37-47% of adjacent pairs are out of order by UMI total,
but the order is clearly cells-first):

### 3.2 Bytes: member 1 (called cells) and member 2 (empties), exon + intron

Subsets are re-encoded with today's production writer through the compiled binding (level 3, 1024 columns per chunk); the
re-encode of the full matrix reproduces the shipped file to the byte for 10 of the 16 matrices (the others, written by a different
zstd build, differ by at most 0.49%).

* **(i)** today's writer: names, permutation, ptr, colsums still inside each member.
* **(ii)** names, permutation, ptr, colsums removed with Track A's costs: rownames -> 8 B vocabulary id; permutation ->
  per-row nnz counts (LEB128 + best of zstd-19/xz, recomputed for the subset); ptr/colsums derived; barcodes -> whitelist
  index in the original relative order (2.5-2.75 B per barcode, Track A); payload as today. Header, chunk table, footer counted.
* **(iii)** (ii) with the chunk payload replaced by the best payload code length on disk. Sources, read at the time of writing:
  per-subset Track D cross-validated code lengths (`M2_featdepth_cv_total` for cells; the smaller of M2 and `amb_loo_bits` for
  empties; `side_H0_kj_mdl` as column-depth side information), checked against the best realized all-column codecs in
  `track_b_codecs*.tsv` (b_rans16) and `track_c_cv.tsv` (c_r2 out-of-sample rows): the nnz-weighted sum of the per-subset code
  lengths is within -1% to +3% of the best realized codec on all 14 matrices (realized higher by 1% on average). Nothing in
  any results table (`idea*`, `track_*`) beats the realized codecs by more than 2.2% on any file; `e1_*` and `e2_*` report no payload bits. These are code-length estimates,
  not decoded bitstreams: the chunk-level (iii) numbers are as good as the models.

* (iii) takes another 4.5-20% off cells (6.6 vs 7.0 b/nnz on brain exon cells, 5.6 vs 6.6 on pbmc_v2_typical exon) and 9-17% off
  empties (9.6 vs 11.7 b/nnz on brain exon empties; the multinomial/ambient floor is 9.4-9.6).
* Gene level for context (exon + intron summed per gene, called cells, today's writer; `results/e4_tiers.tsv`, member `gene`):
  brain_sn_v3_deep 4.20 MB (i), 3.90 MB (ii) against 6.63 MB for the interval-level cells (iii); pbmc_v2_typical 2.46 MB (ii)
  against 3.03 MB. A gene-level first tier is 1.2-1.7x smaller than the interval tier and is a prefix of it if coded
  hierarchically (E3), but is redundant if stored next to it.

### 3.3 Latency model

Rules (stated in the header of `tools/e4_latency.py`): HTTP/2 on an established connection (a cold TLS 1.3 connection adds
2 RTT = 100 ms to every row), requests in a round share the link, `t = sum over rounds (RTT + bytes/bandwidth)`, RTT 50 ms,
no slow start, no decode time. Round 1 of every reader is one suffix range request for the last 64 KiB: central directory
(11.4 KB for the 14-sample bundle, ~1 KB for the one-sample archive modelled for each corpus sample), `manifest.json`
(written last, so adjacent), `study_meta.json`. Scenarios: the first 1024 called cells (exon + intron), all called cells,
everything.

* **today**: first chunk = tail; then `cell_calls.tsv` + the 96-byte headers of exon and intron; then, in one round,
  permutation/ptr/chunk-table prefix, the names block, and the chunks that hold the first 1024 called cells (positions known
  exactly from the data; a real reader guesses). 10 requests, 3 rounds. All cells = best of (a) fetch both members whole,
  2 rounds, and (b) prefix + names + chunks 0..last chunk holding a called cell, 3 rounds, with an *oracle* for that chunk
  index (so (b) is flattering to today). Everything = whole members.
* **tiered (i)**: the cells member and the empties member written by today's writer (same reader logic, smaller members).
* **untiered (ii)**: new container, one member with all columns in today's order, chunk index in the tail manifest, so a
  reader fetches chunks 0..last chunk with a called cell. Isolates what tiering itself adds.
* **tiered (ii), (iii)**: members 1/2/3 as in section 4; the tail request also returns the chunk index, so the first block is
  one more request. 2 requests, 2 rounds.
* untiered (iii) is not reported: per-chunk code lengths for a mixed cell/empty region are not on disk.

## 4. Container proposal

The archive stays a zip64 with STORED members, so every HTTP server, CDN and existing zip reader keeps working and one
`Range` request can address any member.

```
GSE….singlet                         (zip64, STORED, central directory at the end as today)
  samples/<GSM>/cells.pz2            member 1: called cells; column-block-major, 1024 columns per block
  samples/<GSM>/empties.pz2          member 2: empty droplets, ambient-coded; fetched only on demand
  samples/<GSM>/manifest.bin         member 3: derived-on-read manifest + run metadata (~1.5 KB)
  …                                  (next sample)
  manifest.json  study_meta.json  + every samples/<GSM>/manifest.bin   last in the archive, next to the central directory
```

**Member 1 (`cells.pz2`).** A fixed 96-byte header (magic, reference-build vocabulary id, whitelist id, matrix list, n columns,
block size, codec ids), then the chunk index (`offset:u48, length:u32` per block, 10 B each; 40 B for 3.3k cells), then the
blocks. Block *b* holds columns 1024b ... 1024b+1023 of **all matrices of the sample** (exon, intron, sj, vdj): barcodes
as whitelist indices, per-column depth side information, then each matrix's payload. A block is self-describing, so one range
returns decodable cells of every modality. The per-row nnz counts that regenerate the frequency permutation (or, for the E2
coder in ascending row order, the per-feature margins) sit in the header: 0.05-0.15 MB per matrix. Rows are the reference
vocabulary (`vocab_id`), never stored. Deepest cells first (as today), or shallowest first if first-block size matters.

**Member 2 (`empties.pz2`).** Same container; blocks of 1024 empty droplets, ambient-coded (profile from the decoded cells and
from earlier blocks, Idea 2 / Track D `amb_loo`). Nothing in member 1 depends on it.

**Member 3 (`manifest.bin`).**
(a) a recipe id, with the pinned formula, for every derived artifact (table below);
(b) the chunk index of members 1 and 2, duplicated from their headers so that the tail request alone plans every read;
(c) the independent run metadata that today lives in summary.json, pileup_stats.json and provenance.json (STAR input and
uniquely mapped counts, read-level counters, run time and memory, git sha, reference-manifest hash, the cell-caller name):
1.6 KB per sample deflated today, about 1 KB once the derivable fields are gone;
(d) a digest of the decoded arrays of each matrix (the integrity check that survives re-encoding; replaces the per-member
SHA-256 over container bytes that depends on the zstd build).

**Placed at the tail**, next to the central directory: `manifest.json`, `study_meta.json` and every `manifest.bin`
(14 x 1.5 KB for this bundle), so the 64 KiB suffix request that every reader makes first returns the plan for all later reads.
Central directory: 3 entries per sample instead of 10, so 44 entries (3.5 KB) instead of 143 (11.4 KB) for this bundle.

### Recomputed on read, with the pinned formula

| derived artifact | recipe (what the format must pin) | evidence |
|---|---|---|
| colsums (not stored) | uint64 sum of the values of each column | 70/70 |
| ptr | per-column nnz = sum of the value-group counts in the block metadata | 70/70 |
| row permutation | counting sort of per-row nnz, descending, ties by ascending row id (or none, if rows are coded in ascending id) | 70/70 |
| splice_psi | events from `chrom:start-D` / `chrom:end-A` groups of >= 2 junctions; a junction takes the **first event in bytewise-sorted event-id order**; value = float32(count) / float32(event sum), IEEE division (integer sums < 2^24, order irrelevant); **and the quantisation to store**: the shipped files are `rint(PSI)` in {0,1}; the format should either state that or ship float32/uint16 PSI (the member is derived either way, so storing the real PSI costs nothing) | 14/14 byte-identical; 0 ulp |
| cell_calls.tsv | rows = called barcodes, bytewise sorted; `log10_umi` = `%.4f` of the correctly rounded log10 of the exon column sum (0.0000 if 0); `is_cell` TRUE; p-value `0.0000e+00`; method string from the manifest | 21/21 byte-identical |
| summary.json derived fields | n cells; upper median of the called-cell exon sums; upper median of per-cell distinct genes (gene = rowname prefix before the first `_`); genes detected; UMI fraction in called cells; mean reads per cell; exonic/intronic/intergenic fractions; mapping rate and percent; `%.6g` printing | 273/273 |
| pileup_stats.json hits | `exon_hits`, `intron_hits`, `sj_hits`, `umi_unique`, `n_barcodes` = matrix sums / dimensions | 70/70 |
| feature_vocab.json, rownames of exon/intron/vdj | the reference build's vocabulary, versioned by id | identical in every sample |
| gene-level matrix | sum of exon and intron rows with the same rowname prefix | what `SingletBundle` does on the client today |

Only `log10` needs a library-independence note: it reproduced on all 127,105 rows, but the format should say "correctly
rounded" (or define it with an integer table) rather than "libm".

### What stays

The count matrices (exon, intron, sj, vdj), the sj junction list (independent per sample; a study-level junction vocabulary would
remove ~3.6x of it, Track A), the called set (as the split between members 1 and 2), the barcodes, and the run metadata above.
`mt_heteroplasmy.1pz` stubs disappear (an absent member is an empty matrix); real heteroplasmy matrices would be independent.

### Reader, in requests

| goal | today | proposed |
|---|---|---|
| first 1024 cells | suffix; `cell_calls.tsv` + 2 headers; then per matrix prefix + names + chunks: 10 requests, 3 rounds | suffix (central directory + all manifests); one range for block 0 of `cells.pz2`: **2 requests, 2 rounds** |
| all called cells | 4 requests / 2 rounds (whole members) or ~10 requests / 3 rounds (selective) | suffix; one range for `cells.pz2`: 2 requests, 2 rounds |
| everything | 4 requests, 2 rounds | suffix; one range over `cells.pz2` + `empties.pz2` (adjacent): 2 requests, 2 rounds |

So the plan's "no regression" holds and improves: the number of rounds never rises, the bytes of the first block fall 4-42x.
Limits: for archives with more than ~30 samples the per-sample manifests no longer fit in a 64 KiB tail; the fallback is one more
round (the sample's manifest, located through the central directory), i.e. 3 rounds, still no worse than today. Servers must
honour suffix ranges (`Range: bytes=-65536`); `data.singlet.bio` serves ranges (the corpus was fetched that way).

### Lossless claim and compatibility

*Bit-exact means the decoded matrix and the derived artifacts, not the container bytes* (a v1 file's bytes depend on the zstd
build that wrote it; Track A). Column order: if cells and empties each keep the relative order of the original file, the
original order is recovered from the merge bitmap (n bits; 2.5 KB for 84k columns at its entropy, 10.5 KB raw), and I counted
this order-preserving variant everywhere. If columns are written in whitelist order instead, barcodes cost 0.86 B rather than
2.75 B each (Track A: 72.5 KB vs 232 KB on brain_sn_v3_deep) and the original discovery order is no longer recoverable;
`bytes_ii_canon` / `bytes_iii_canon` in `e4_tiers.tsv` give that variant. A v1 reader can still open the bundle if
`feature_vocab.json` and the v1 members are produced from the v2 ones by the recipes above (a v2 -> v1 shim is the same code).

## 5. What I did not do / caveats

* (iii) is a code-length estimate from Track D's cross-validated models, validated against the realized codecs on all 14
  matrices (within -1%..+3%); no new bitstream was written. E1 and E2 results were not on disk when I finished; nothing in
  `idea*_run*.tsv` or the other results tables was better than the realized codecs by more than 2.2% (tcell_5p intron, idea3 joint),
  and some of those runs are in-sample.
* Latency is a model (no slow start, no server think time, no decode, warm connection). The first-chunk and all-cells rows for
  today use exact chunk positions and an oracle for the last chunk with a called cell, so today's numbers are flattering.
* Corpus samples are modelled as one-sample archives; only tumor_3p has sj/vdj/psi (from the bundle).
* The three bundle members `summary.json`, `pileup_stats.json`, `provenance.json` were only available for the 14 bundle samples;
  the 7 corpus samples were checked for the five fields that need only the matrix and the called set.
* Heteroplasmy was not tested (all stubs). Cell calls were tested only for `star_solo`, the only method present; EmptyDrops
  (Monte Carlo, whole-whitelist ambient, `export.h:570`) cannot be regenerated from the bundle and would make the called set and
  the p-values independent.
* The `round-half-even` finding is inferred from data, not from a code path: I could not find which writer produced it.
