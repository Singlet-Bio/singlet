## Where an item's time goes at head (2026-11-14; runs 815178, traced 815201; tools $W/jobs/gpu-runtime/ana/)

GPU slots (2 per GPU, 3 items in flight) are 83-91 % used: ~110 slot-s per item (map 54, all-site ~22, pileup 15, hand-off 10,
non-host classify 6.5, Solo 3.3) against ~126 available; at least one request queued 45 % of the time. Cutting wall outside the
slots can raise node rate only ~10-20 % more; each slot-second removed per item raises the ceiling ~0.9 %. GPUs not compute-bound
(SM ~62 %). Item end: the non-host screen (43 s; EM 26.6 s at the 500-iteration cap) starts only after the pileup host pass although
STAR's child exits ~34 s earlier; the main thread then waits 8.5 s mean for it after export validation, plus ~3 s teardown.
Next wave: rt/tailend (early non-host start, all-site wait at first use, fast exit), rt/maphold (overlap inside mapping hold 1),
3-slot experiment.

**3 slots per GPU: no.** 3 x 31 GB + 16.4 GB shared index does not fit in 93 GB; at 23 GB per slot (g052, head binary):
slots3 815211 8.28 steady / 7.30 whole, 2 items OOM in the hand-off pass; slots2 815212 9.19 / 8.32; slots3b 815213 8.12 / 7.36,
non-host server OOM -> samples loaded the index themselves. Queues vanish (>=1 waiter 45 % -> 7-19 %), but every hold gets
longer at the smaller budget (map hold1 ~69 s). The slot budget is a planning tally (memBudget), not a hard cap; the non-host
index (24.9 GB) sits outside it. Cheaper route: shorter holds inside 2 slots.

**Mapping hold (rt/maphold 1a62de02, not merged yet):** H1DEV (read hashes stay on the device through dedup) cuts rc.dedup
4.65 -> 2.84 s per item; LANED2H (lane A/M result copies on a thread) stalls 9-10 s on 3 of 24 items. Pair on g051: on
9.123 / 8.488, off 9.434 / 8.593, set hash identical; gates 815216 and forced 815217 8/8. Hold 1 ~50 s of which ~27 s is lane
kernels; removable host/transfer share ~5-7 s.

**Tail end (rt/tailend d0209d17 + b5f3904e, NOT merged):** early non-host screen (at STAR exit), all-site wait at first use,
fast exit. Identical (gate 815230 8/8; node file lists + md5 identical). Same-binary pair `bin/tailend-2` on g052: on 815231
9.013 / 8.243, 208 s; off 815232 9.469 / 8.388, 204 s. Join wait 9.6 -> 0.1 s and all-site wait 7.8 -> 1.4 s, but map +9 s and
pileup +6 s: the early screens compete with other items' map/pileup for CPU and slots. Fast exit ~0.8 s. Bug found and fixed on
the branch: an early screen without the pool's non-host server made its own CUDA context and cudaDeviceReset killed the
pileup's (4/8 gate core dumps); early start now needs SINGLET_NONHOST_SERVER. Lesson: with slots ~85 % busy, moving work
earlier moves contention; only fewer slot-seconds per item (or less CPU in the slot-holding phases) helps.
